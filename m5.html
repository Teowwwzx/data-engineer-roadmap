Computer Science & Cloud Infrastructure计算机原理与云基础设施

This is the layer most people skip — and it's the layer that separates someone who can write a script from someone who can explain why it takes four hours and how to make it take four minutes. You don't need a CS degree. You need the mental model.

这是大多数人跳过的一层——也正是这一层，区分了"会写脚本的人"和"能解释它为什么跑四小时、以及怎么让它跑四分钟的人"。你不需要计算机学位，你需要的是那个心智模型。

In plain English — the whole milestone in 4 lines大白话版 —— 四行讲完这个阶段
  • CPU is fast, memory is slower, disk is far slower, network is furthest. Almost every slow thing is walking too far, too often.
  • C is translated once before running. Python is translated line by line, every time — which is why it is slower.
  • pandas is fast because underneath it is not Python. "Vectorise it" means: let that faster layer do the work.
  • The cloud is renting someone else's computers by the minute. Put your database somewhere the internet cannot reach.
  • CPU 最快，内存慢一点，磁盘慢得多，网络最远。几乎所有"慢"，都是走得太远、走得太频繁。
  • C 在运行前一次性翻译完；Python 每次都逐行翻译 —— 这就是它慢的原因。
  • pandas 快，是因为它底下根本不是 Python。"向量化"的意思就是：让底下那层更快的东西去干活。
  • 云就是按分钟租别人的电脑。把你的数据库放在互联网够不到的地方。

1How a computer actually works计算机到底是怎么运转的

Why should a data person care about hardware?做数据的人为什么要关心硬件？

Because every performance problem you will ever face is the same story in different clothes: something is walking to the cold room too many times.

Without this model, "it's slow" is a mystery and you'll try random fixes — a bigger machine, more threads, a different library. With it, you can reason: is this reading from disk in a loop? Is it shipping data over the network row by row? Is it running out of RAM and swapping? Three questions, and one of them is almost always the answer.

因为你将来遇到的每一个性能问题，都是同一个故事换件衣服：有人在反复跑去冷藏室。

没有这个模型，"它很慢"就是个谜，你只能乱试——换更大的机器、加线程、换个库。有了它，你可以推理：它是不是在循环里反复读磁盘？是不是在逐行走网络？是不是内存不够在换页？三个问题，答案几乎总在其中。

How it used to work以前是怎样
  • CPUs got faster every year, so slow code got faster for free. You could wait for hardware to fix you.
  • Spinning hard disks — a physical arm moving to a physical track. Random reads were catastrophically slow.
  • RAM was scarce and expensive; every byte was budgeted.
  • Scaling up meant one bigger, hotter, more expensive machine.
  • CPU 每年都变快，慢代码会自动变快。等硬件替你解决就行。
  • 机械硬盘——一条物理磁臂移动到物理磁道。随机读慢得离谱。
  • 内存又少又贵，每个字节都要精打细算。
  • 扩容 = 换一台更大、更热、更贵的机器。
→
How it works now现在是怎样
  • Single-core speed stopped improving much around 2005. Free speedups ended; now you get more cores, and only parallel code benefits.
  • SSDs removed the moving parts, but disk is still ~1,000× slower than RAM.
  • RAM is plentiful — so "load it all into memory" is often the correct, boring fix.
  • Scaling means more machines, which is why distributed tools (Spark, warehouses) exist at all.
  • 单核速度大约在 2005 年后基本停滞。免费提速结束了，现在给你的是更多核，只有并行代码才受益。
  • SSD 去掉了机械部件，但磁盘仍然比内存慢约 1000 倍。
  • 内存变得充裕——所以"全部加载进内存"常常就是那个正确又无聊的解法。
  • 扩容意味着更多台机器，这也正是分布式工具（Spark、数仓）存在的全部理由。

Why this matters right now: the fact that single-core speed plateaued is the reason your job exists in its current form. If computers had kept doubling in speed, nobody would need distributed data engineering.

为什么这件事现在很重要：单核速度触顶，正是你这份工作以今天这种形态存在的根本原因。如果电脑一直在翻倍变快，就没人需要分布式数据工程了。

🧪 The bench, the shelf, and the cold room🧪 实验台、架子、冷藏室

The CPU is you — the only thing that actually does work, and you can only hold one or two tubes at a time. RAM is your benchtop: fast to reach, small, and wiped clean every night (that's why unsaved work vanishes when power is lost). Disk / SSD is the cold room down the corridor: enormous, permanent, and slow — you have to get up and walk there.

CPU 是你本人——唯一真正在干活的东西，而且一次只拿得住一两支管。内存是你的操作台：伸手就够到，但小，而且每晚清空（这就是断电后未保存的东西会消失的原因）。磁盘/SSD 是走廊尽头的冷藏室：巨大、永久、但慢——你得站起来走过去。

Why your script died你的脚本为什么挂了

MemoryError / process killed = you tried to put more on the benchtop than fits. Fix: process in chunks, or use a tool that streams (Polars, DuckDB).

MemoryError / 进程被杀 = 你想往操作台上放的东西超过了它的容量。解法：分块处理，或用支持流式的工具（Polars、DuckDB）。

Why your script is slow你的脚本为什么慢

Usually not the CPU. It's reading the same file repeatedly, querying row-by-row inside a loop, or shipping data over the network a thousand times. Do the work in bulk, once.

通常不是 CPU 的问题。是反复读同一个文件、在循环里逐行查数据库、或者把数据在网络上来回搬一千次。改成批量、一次搞定。

If you don't have this model: you'll respond to slowness by asking for a bigger machine. Often the machine was never the problem, the money is spent, and the job is still slow — now with a bigger bill attached.

The classic beginner pattern: a loop that opens a database connection, runs one query, closes it — a million times. That's a million round trips. The same work as one query returning a million rows, done a million times more expensively.

The cloud version of the mistake: reading a file from object storage inside a loop. Each read crosses a network. Ten thousand small reads can take an hour where one bulk read takes four seconds.

没有这个模型：一慢你就去申请更大的机器。而机器往往从来不是问题，钱花了，任务还是慢——只是账单更大了。

新手最经典的模式：循环里开一个数据库连接、跑一条查询、关掉——重复一百万次。那是一百万次往返。和"一条查询返回一百万行"做的是同样的事，但代价高一百万倍。

这个错误的云版本：在循环里从对象存储读文件。每次读都跨一次网络。一万次小读可能要一小时，而一次批量读只要四秒。

If a nanosecond were one second, reading from disk would take about a day and a half. That is why "just load it all into memory" is usually the fix.如果一纳秒等于一秒，那么读一次磁盘大约要一天半。这就是为什么"干脆全加载进内存"通常就是解法。

◈ Real-world example◈ 真实场景

A colleague's enrichment script takes 6 hours for 200,000 records. They ask for a bigger server.

You read the code. Inside the loop, for every record, it opens a connection and runs one SELECT. That's 200,000 network round trips at roughly 100 ms each — about 5.5 hours of pure waiting, with the CPU idle almost the entire time. A bigger server would change nothing.
The fix: one query that fetches all the lookup values into a dictionary, then look up in memory. Runtime drops from 6 hours to about 90 seconds. No new hardware, no new library — just knowing which line in the chart above the code was standing on.

同事的数据补全脚本处理 20 万条要跑 6 小时。他来申请一台更大的服务器。

你读了代码。循环里，每条记录都开一次连接、跑一条 SELECT。那就是 20 万次网络往返，每次约 100 毫秒——大约 5.5 小时纯等待，而 CPU 几乎全程闲着。换更大的服务器毫无用处。
解法：用一条查询把所有对照值取进一个字典，然后在内存里查。运行时间从 6 小时降到约 90 秒。没有新硬件、没有新库——只是知道了这段代码站在上面那张图的哪一层。

2Why C is fast and Python is slow为什么 C 快而 Python 慢

Why does this matter if you'll never write C?你永远不会写 C，为什么还要懂这个？

Because it explains the single most valuable optimisation in data work, and why it feels like magic.

pandas and NumPy are fast because they aren't really Python — underneath, they're compiled C. df["a"] * 2 is one C operation over a million values. A Python for loop doing identical arithmetic is a million separate interpreted steps. Same maths, 50–100× difference.

The purpose in one line: when someone says "vectorise it," they mean stop doing the work in Python and hand the whole array to the C underneath. Now you know why that works.

因为它解释了数据工作里最值钱的一项优化，以及为什么它像魔法。

pandas 和 NumPy 之所以快，是因为它们其实不是 Python——底下是编译好的 C。df["a"] * 2 是对一百万个值的一次 C 运算；而做同样算术的 Python for 循环，是一百万个各自被解释的步骤。同样的数学，差 50–100 倍。

一句话说清目的：当有人说"向量化一下"，意思是别在 Python 里做这件事，把整个数组交给底下的 C。现在你知道为什么这管用了。

The old trade-off以前的权衡
  • Choose one: fast to write (Python, R) or fast to run (C, Fortran).
  • Serious numerical work meant writing C and suffering.
  • Prototypes were rewritten from scratch in another language for production. Twice the work, two chances to introduce bugs.
  • 二选一：写得快（Python、R）或跑得快（C、Fortran）。
  • 正经的数值计算意味着写 C 并且忍受它。
  • 原型上生产时要用另一种语言从头重写。双倍工作量，两次引入 bug 的机会。
→
How it works now现在是怎样
  • You write Python; the heavy loops run in compiled code you never see (NumPy, pandas, PyTorch).
  • New tools go further: Polars and DuckDB are written in Rust/C++ with a Python interface.
  • The skill shifted from "write fast code" to "stay out of the interpreter's way".
  • Same source runs on a laptop and on a hundred machines, unchanged.
  • 你写 Python，重循环跑在你看不见的编译代码里（NumPy、pandas、PyTorch）。
  • 新工具走得更远：Polars 和 DuckDB 用 Rust/C++ 写，外面套 Python 接口。
  • 技能从"写出快的代码"变成了"别挡着解释器的路"。
  • 同一份源码，在笔记本上和一百台机器上都能跑，不用改。
🧪 A translated protocol vs a live interpreter🧪 译好的方案 vs 现场翻译

C is compiled. Before you run anything, the whole protocol is translated once into the machine's native language, checked, and optimised. Slow to prepare — then pure speed.

Python is interpreted. A translator stands beside the bench converting each line as you reach it, every single time, including inside a loop that runs a million times.

C 是编译的。运行之前，整份方案先被一次性翻译成机器的母语，检查、优化。准备慢——然后一路飞。

Python 是解释的。有个翻译站在台边，你走到哪句他翻哪句，每次都翻，包括在一个跑一百万次的循环里。

If you write Python loops over big data: jobs that should take a minute take an hour. It works in testing on 1,000 rows and dies in production on 10 million — the worst possible place to find out.

If you assume "Python is just slow" and give up: you'll reach for Spark and a cluster for a dataset that DuckDB would handle on your laptop in nine seconds. Distributed systems have real operational cost; reaching for one you don't need is an expensive habit.

If you never learn what a compiler does: type errors that C would catch before running will reach production in Python. That's the trade you accepted — which is exactly why tests and type hints matter more in Python, not less.

如果对大数据写 Python 循环：本该一分钟的任务要跑一小时。在 1000 行的测试里没事，在一千万行的生产环境挂掉——这是最糟的发现地点。

如果认定"Python 就是慢"然后放弃：你会为一个 DuckDB 在你笔记本上九秒就能搞定的数据集，去上 Spark 和集群。分布式系统有真实的运维成本，动不动就上一个用不着的，是个昂贵的习惯。

如果从不了解编译器做什么：那些 C 在运行前就能抓住的类型错误，在 Python 里会一路跑到生产环境。这就是你接受的那笔交易——也正因如此，测试和类型标注在 Python 里更重要，而不是更不重要。

◈ Real-world example◈ 真实场景

A daily job that scores 2 million rows takes 40 minutes and is starting to overrun into business hours.

The scoring is a Python for loop applying four arithmetic rules per row. Rewritten as four vectorised pandas expressions on whole columns, the same job finishes in 25 seconds — a 96× improvement, on identical hardware, from a change of about eight lines.
What you actually did: moved the work from the interpreter into the compiled C underneath. What it looked like to your manager: you made something 96× faster in an afternoon. This one insight will pay for the whole of Milestone 5.

一个每天给 200 万行打分的任务要跑 40 分钟，已经开始拖到上班时间了。

打分逻辑是一个 Python for 循环，对每行应用四条算术规则。改写成四条对整列的向量化 pandas 表达式后，同样的任务 25 秒跑完——同样的硬件上快了 96 倍，改动约八行代码。
你实际做的：把计算从解释器搬到了底下编译好的 C 里。在你主管眼里：你一个下午把一个东西提速了 96 倍。仅这一个认知，就够回本整个阶段五。

3Cloud platforms — AWS, Azure, networking, security云平台 —— AWS、Azure、网络与安全

Why rent computers instead of buying them?为什么租电脑而不是买？

Because demand is spiky and hardware is not. Your nightly job needs 64 machines for one hour and zero machines for the other 23. Buying 64 machines means paying for 23 hours of idle metal, plus the room, the cooling, the electricity and the person who replaces failed drives.

There's a second reason that matters more day to day: time to try things. Testing an idea used to mean a purchase order and six weeks. Now it's four minutes and about a dollar. That changes what's worth attempting.

因为需求是尖峰式的，而硬件不是。你的每晚任务需要 64 台机器跑一小时，剩下 23 小时一台都不用。买 64 台意味着为 23 小时的闲置金属付钱，外加机房、制冷、电费，以及换坏硬盘的那个人。

还有个日常更重要的理由：试错的时间成本。以前验证一个想法要走采购流程等六周，现在是四分钟、大约一美元。这改变了"什么值得一试"。

How it used to work以前是怎样
  • Buy a server. Wait six weeks. Rack it in a room in your building. Hope you sized it right.
  • Capacity was a guess made a year in advance, and you paid for the peak all year.
  • Disaster recovery meant a second room in a second city that you hoped never to use.
  • Security was mostly "it's inside our building, so it's safe."
  • 买一台服务器，等六周，装进自家楼里的机房，祈祷容量估对了。
  • 容量是提前一年拍脑袋定的，而且全年按峰值付钱。
  • 灾备意味着在另一个城市再建一个机房，并祈祷永远用不上。
  • 安全基本上是"它在我们楼里，所以是安全的"。
→
How it works now现在是怎样
  • Rent by the minute. Need 64 machines for an hour? Have them in four minutes; give them back after.
  • Autoscaling matches capacity to actual demand, hour by hour.
  • Storage is effectively unlimited and replicated across data centres by default.
  • Security is explicit and identity-based: nothing is trusted just for being inside the network.
  • 按分钟租。要 64 台跑一小时？四分钟内到位，用完还回去。
  • 自动伸缩让容量按小时贴合真实需求。
  • 存储几乎无限，且默认跨数据中心复制。
  • 安全是显式的、基于身份的：不会因为"在内网里"就被信任。

The trap that came with it: the cost moved from a one-time purchase you noticed to a monthly bill you don't. A forgotten test cluster costs nothing to create and thousands over a quarter. Billing alerts are not optional.

随之而来的陷阱：成本从"你会注意到的一次性采购"变成了"你不会注意到的月账单"。一个忘了关的测试集群，创建时不花钱，一个季度下来是几千块。账单告警不是可选项。

🧪 Renting a national facility instead of building your own🧪 租用国家级平台，而不是自建

You could buy a mass spectrometer, house it, service it, staff it — and pay for all of that whether you run one sample a month or a thousand. Or you could send samples to a shared facility and pay per run. Same reasoning, same trade-offs.

你可以买一台质谱仪，给它腾地方、做保养、配人——不管你一个月跑一份样本还是一千份，这些钱都得花。或者你把样本送到共享平台，按次付费。同样的逻辑，同样的取舍。

Networking, in the five terms you'll actually hear网络：你真正会听到的五个词

IP address — a machine's street address. Port — which door on that building (443 = secure web, 5432 = PostgreSQL).

DNS — the phone book: turns lab.example.com into an IP. "It's a DNS issue" is a real and extremely common diagnosis.

Firewall / security group — the door policy: which addresses may knock on which ports. When something "can't connect" and the code is fine, this is usually why.

Public vs private subnet — public is reachable from the internet, private is not. Your database belongs in a private subnet. Always.

TLS / HTTPS — the sealed envelope. Everything in transit should be encrypted, without exception.

IP 地址——机器的门牌号。端口——这栋楼的哪扇门（443 = 安全网页，5432 = PostgreSQL）。

DNS——电话簿：把 lab.example.com 翻译成 IP。"这是 DNS 问题"是一个真实且极其常见的诊断。

防火墙 / 安全组——门禁策略：哪些地址可以敲哪些端口。当代码没问题却"连不上"时，通常就是它。

公有 vs 私有子网——公有可从互联网访问，私有不行。你的数据库属于私有子网。永远。

TLS / HTTPS——密封信封。传输中的一切都应该加密，没有例外。

Security habits to build in your first year第一年就该养成的安全习惯

Never put a password or key in your code. Not even temporarily, not even in a branch you'll delete. Git remembers forever, and bots scan public repos within minutes.

Least privilege, always. If your pipeline only reads, give it read-only credentials. Damage is bounded by permissions granted.

Separate environments. Dev, staging, production — different credentials. Everyone who has run a DELETE against the wrong database learned this the same way.

Know what's sensitive. Personal, health and financial data carry legal obligations. When in doubt, ask before copying it anywhere new — including into an AI prompt.

Turn off what you're not using, and set a billing alert on day one.

绝不要把密码或密钥写进代码。哪怕只是临时，哪怕是在一条你打算删掉的分支上。Git 会永远记得，而机器人几分钟内就会扫到公开仓库。

永远最小权限。管道只读，就给只读凭据。损失的上限由你授予的权限决定。

环境要分开。开发、预发、生产——用不同的凭据。每一个对着错误的数据库执行过 DELETE 的人，都是这样学会的。

知道什么是敏感数据。个人、健康、财务数据都带法律义务。拿不准就先问，再往新地方复制——包括粘进 AI 的提示词。

不用的就关掉，并且第一天就设好账单告警。

If you put a database in a public subnet: automated bots will find it within minutes of it coming online. Not "might" — will. The internet is continuously port-scanned by machines looking for exactly this.

If you hardcode a credential and push it: assume it is compromised the moment it hits a public repo, even if you delete it in the next commit. Git history keeps it, and scanners are faster than you.

If you don't set a billing alert: a misconfigured job or a forgotten cluster runs for three weeks. You find out at the end of the month, and the conversation about it is not about engineering.

If you don't understand subnets and security groups: you'll debug "connection refused" in your code for a whole day when the answer was a firewall rule someone changed on Tuesday.

如果把数据库放在公有子网：它上线几分钟内就会被自动化程序发现。不是"可能"，是"一定"。互联网上一直有机器在扫端口，找的就是这个。

如果把凭据硬编码然后推上去：就当它在进入公开仓库那一刻已经泄露了，哪怕你下一次提交就删掉。Git 历史会留着，而扫描器比你快。

如果不设账单告警：一个配置错的任务或忘关的集群会跑三个星期。你月底才发现，而那场对话谈的不是技术。

如果不懂子网和安全组：你会花一整天在代码里查"connection refused"，而答案是周二有人改了一条防火墙规则。

◈ Real-world example◈ 真实场景

Someone spins up a GPU instance to test a model on a Friday afternoon and forgets about it.

It sits idle all weekend, all month. Nobody notices because it works — nothing is broken, so nothing alerts. At month end the bill is several thousand dollars higher and finance wants an explanation.
None of this is a technical failure. It's the direct consequence of a cost model where creating something expensive takes four clicks and forgetting it takes zero. This is why a billing alert on day one is worth more than most optimisations you'll ever write — and why "turn off what you're not using" is a real engineering habit, not housekeeping.

有人周五下午开了一台 GPU 实例测模型，然后忘了。

它整个周末、整个月都闲着。没人发现，因为它"能用"——没坏，所以没有告警。月底账单多出几千美元，财务来要说法。
这不是技术故障。它是一种成本模型的直接后果：创建一个昂贵的东西只要四次点击，而忘掉它需要零次操作。这就是为什么"第一天就设账单告警"比你以后写的大多数优化都值钱——也是为什么"不用就关掉"是一个真正的工程习惯，而不是打扫卫生。

⚡ Challenge⚡ 挑战

Take something slow and make it embarrassingly fast把一个慢东西，快到令人尴尬

★★★

Write a script that is deliberately, catastrophically badly written — a Python loop over a million rows, opening a file inside the loop, querying row by row. Time it. Then fix it in stages and time it after each one.

Vectorise the arithmetic. Read the file once instead of a million times. Replace the row-by-row query with one bulk fetch into a dictionary. Then try the same job in DuckDB or Polars and time that too. Keep the numbers.

故意写一个差到离谱的脚本——用 Python 循环处理一百万行，在循环里打开文件、逐行查数据库。计时。然后分阶段修复，每修一步计一次时。

把算术向量化。文件只读一次而不是一百万次。把逐行查询换成一次批量取回到字典里。然后用 DuckDB 或 Polars 做同样的事，也计一次时。把这些数字记下来。

You've won when达成条件 You have a table of five timings on the same machine, and you can explain each drop by pointing at a specific layer of the memory hierarchy. Not "it got faster" — why it got faster. 你有一张同一台机器上的五个耗时数据表，而且每一次下降你都能指着存储层级里的某一层解释清楚。不是"变快了"，而是为什么变快了。
Show me how to approach it给我一点思路

1. Use time.perf_counter() around each version, and print the ratio against the first. Ratios are what people remember.

2. Fix one thing at a time. If you fix three things and it gets 90× faster, you have learned nothing about which one mattered.

3. Expect the biggest single win to come from removing round trips — the file open or the per-row query — not from the arithmetic. That is the memory hierarchy telling you where it actually hurts.

4. Then push it further than is reasonable: make the file bigger than your RAM. Watch it die. Fix it with chunking, then with DuckDB streaming, and note that DuckDB barely noticed.

5. Write the whole thing up in the README with the timing table. This is the single most persuasive artefact a junior engineer can own — it is evidence that you understand what is underneath the code, not just the code.

1. 用 time.perf_counter() 给每个版本计时，并打印相对第一版的倍数。倍数才是别人会记住的东西。

2. 一次只改一件事。如果你一口气改了三处、快了 90 倍，你其实完全不知道是哪一处起了作用。

3. 预期最大的一次提速来自"消灭往返"——去掉循环里的开文件或逐行查询——而不是来自算术。这就是存储层级在告诉你真正疼的地方在哪。

4. 然后往不合理的方向再推一步：把文件弄得比内存还大，看着它挂掉。先用分块修好，再用 DuckDB 流式处理，然后注意到 DuckDB 几乎毫无压力。

5. 把整个过程连同耗时表写进 README。这是一个初级工程师能拥有的最有说服力的作品——它证明了你理解代码底下那一层，而不只是代码。

One focused weekend. Then, the first time a colleague says "we need a bigger server," you will be the person in the room who asks to see the code first.一个专注的周末。之后，当同事第一次说"我们需要更大的服务器"时，你会是屋里那个先要求看代码的人。

Check yourself · Milestone 5自我检验 · 阶段五

Your pandas loop over 2 million rows takes 40 minutes. What's most likely to fix it?你的 pandas 循环处理 200 万行要 40 分钟。最可能的解法是什么？

Vectorise. The bottleneck is the Python interpreter translating your loop body 2 million times. Handing the entire column to NumPy runs the same arithmetic in compiled C — routinely 50–100× faster on the same hardware.向量化。瓶颈是 Python 解释器把循环体翻译了 200 万次。把整列交给 NumPy，同样的算术在编译好的 C 里跑——同样的硬件上通常快 50–100 倍。

Where should a production database live?生产数据库应该放在哪？

Private subnet. Anything with a public IP is being port-scanned by automated bots continuously — usually within minutes of coming online. Access it through a bastion host or VPN instead.私有子网。任何有公网 IP 的东西都在被自动化程序持续扫描——通常上线几分钟内就开始。要访问就通过跳板机或 VPN。
