First, the most important idea in this guide先说这份指南里最重要的一件事

You were hired as a "Data Engineer." Your colleague is a "Software Engineer." Someone else is an "AI Engineer." These are labels on an org chart, and they get renamed every few years.

你的岗位叫"数据工程师"，同事叫"软件工程师"，另一个人叫"AI 工程师"。这些只是组织架构图上的标签，每隔几年就会换一批说法。

The titles change. The foundations don't. Everyone is standing on the same bedrock — how a machine computes, how data is stored, how two computers talk, how work gets deployed and kept safe.

头衔会变，地基不会。所有人踩的是同一块岩层——机器怎么计算、数据怎么存储、两台电脑怎么对话、代码怎么上线并保证安全。

An AI can now write a SQL query, a React component, or a Python script faster than you can. What it cannot do is know whether the answer is right. That judgment comes from understanding the layer underneath — and that's exactly what this roadmap builds. Learn the bedrock, and any title becomes reachable.

今天的 AI 写一条 SQL、一个 React 组件、一段 Python 脚本，都比你快。但它做不到的是判断这个答案对不对。这份判断力来自你对底下那一层的理解——而这正是这条路线图要建立的东西。地基打好了，任何头衔都在射程之内。

⌨ Try this right now — on any website in the world⌨ 现在就试试 —— 对世界上任何一个网站

Here is the thing nobody tells beginners: every website you have ever visited is just HTML, CSS and JavaScript, sent to your computer as plain text. Google, your bank, this page. The server does not send a picture of a page — it sends the skeleton, the clothes and the nervous system, and your browser assembles the body locally.

Which means you already own a copy of every site you visit, and you can open it up. Press F12 (or Cmd+Option+I on a Mac) on any page:

Elements — the skeleton. Hover a line and the matching part of the page lights up. Edit the text and it changes in front of you (only on your screen — refresh and it's back).
Styles — the clothes. Change a colour and watch it repaint instantly.
Console — the nervous system talking. Errors appear here. So do your own console.log() messages.
Network — every request the page makes, with its status code and the exact JSON that came back.

This is not a beginner's toy. It is the same tool professionals use every day, and it is why a data engineer can prove in twenty seconds whether a wrong number came from the pipeline or from the page. Open it on a site you use daily and just look around for five minutes. Nothing you do there can break anything.

有件事没人会告诉初学者：你访问过的每一个网站，本质上都只是 HTML、CSS 和 JavaScript，以纯文本的形式发到你的电脑上。谷歌、你的银行、这个页面，都是。服务器发过来的不是一张页面的图片——它发来的是骨架、衣服和神经系统，然后由你的浏览器在本地把这具身体组装出来。

这意味着你手上其实已经有了每个网站的一份副本，而且你可以把它打开。在任意页面按 F12（Mac 上是 Cmd+Option+I）：

Elements（元素）——骨架。鼠标划过某一行，页面上对应的部分就会高亮。你甚至能直接改文字，页面当场就变（只在你的屏幕上，刷新就还原）。
Styles（样式）——衣服。改一个颜色，立刻重新上色。
Console（控制台）——神经系统在说话。报错出现在这里，你自己写的 console.log() 也出现在这里。
Network（网络）——页面发出的每一次请求，带状态码和返回的原始 JSON。

这不是给初学者玩的玩具，它就是专业人员每天用的同一个工具——也正是数据工程师能在二十秒内证明"这个错数字来自管道还是来自页面"的原因。找一个你每天都用的网站打开它，随便看五分钟。你在里面做的任何操作都弄不坏任何东西。

HTML the skeleton骨架

Bones. What exists, and how the parts connect. Ugly on its own, but nothing can stand without it.

HyperText Markup Language — the tags that define headings, paragraphs, tables, buttons.

骨头。有什么、各部分怎么连接。单独看很难看，但没有它一切都立不起来。

超文本标记语言 —— 用标签定义标题、段落、表格、按钮。

CSS the clothes & skin衣服与皮肤

Appearance. Colour, spacing, size, where things sit. Take it away and the body still stands — it just looks like a hospital X-ray.

Cascading Style Sheets — rules that say "every h1 is teal and 20px."

外观。颜色、间距、大小、东西摆在哪。拿掉它，身体照样站着——只是看起来像一张 X 光片。

层叠样式表 —— 用规则说"所有 h1 都是青色、20 像素"。

JavaScript the nervous system神经系统

Reaction. You touch something hot, the hand moves. You click, the number changes. Without it the body is a very well-dressed statue.

The language that runs inside the browser and reacts to events.

反应。碰到烫的，手就缩回来；你一点击，数字就变。没有它，身体就是一尊穿得很讲究的雕像。

运行在浏览器里、对事件作出反应的语言。

Python the brain, out of sight看不见的大脑

The thinking happens somewhere the visitor cannot reach. Decisions, rules, judgement — deliberately kept off the user's machine.

The backend language where your real logic and data access live.

思考发生在访客够不到的地方。决策、规则、判断——刻意不放在用户的机器上。

后端语言，你真正的业务逻辑和数据访问都在这里。

Apache / Nginx the receptionist前台接待

Sits at the front door all day. Someone knocks; it works out what they want, fetches the right file or passes the request to the right person, and hands back an answer. It never does the analysis itself — it just answers the door, thousands of times a second, and never gets tired.

A web server. It receives HTTP requests and returns responses — serving files directly, or forwarding to your Python app.

整天坐在大门口。有人敲门，它判断对方要什么，取出对应的文件、或者把请求转给该处理的人，然后把答案递回去。它从不亲自做分析——只负责应门，每秒几千次，而且从不喊累。

Web 服务器。接收 HTTP 请求并返回响应——直接提供文件，或转发给你的 Python 应用。

API the request slip申请单

A standard form between two parties who don't want to walk into each other's building. "Run test X on sample Y." You fill in their form; they send back their standard report. Neither side has to know how the other works inside.

Application Programming Interface — an agreed set of requests a system will answer, and the shape of the answers.

两方之间的标准表单，谁都不用走进对方的楼里。"对 Y 号样本做 X 项检测。"你填他们的表，他们回一份标准报告。两边都不需要知道对方内部怎么运作。

应用程序接口 —— 一套约定好的、系统会回应的请求，以及回应的固定形状。

Framework框架 the prefab building预制建筑

The foundations, plumbing, wiring and load-bearing walls are already poured. You decide the layout of the rooms. You could pour your own concrete — but you'd get the drainage wrong, and the drainage is the part that floods.

Flask, React, Django — pre-built infrastructure you fill in with your own logic.

地基、水管、电线、承重墙都已经浇好了，你只决定房间怎么分。你当然可以自己浇混凝土——但排水一定会做错，而排水正是会淹水的那部分。

Flask、React、Django —— 现成的基础设施，你往里面填自己的逻辑。

Database数据库 the sample freezer样本冷冻柜

Everything labelled, indexed, findable, and safe when the power flickers. Not a pile of boxes — a system where two people can put things in at the same time without ruining each other's work.

PostgreSQL, MySQL, SQLite — stores data in related tables and answers SQL queries.

一切都贴好标签、建好索引、随时能找到，停电闪一下也不会丢。它不是一堆纸箱——而是一套两个人同时往里放东西也不会互相毁掉的系统。

PostgreSQL、MySQL、SQLite —— 用关联的表存数据，并回答 SQL 查询。

Git the lab notebook实验记录本

Dated, signed, never erased. You can reconstruct exactly what the code looked like on 14 March, and read why it was changed. Plus something paper never had: a parallel page where you can try a risky idea without touching the working version.

A version control system. Tracks every change, supports branches and merges.

有日期、有签名、从不涂改。你能精确还原 3 月 14 日代码长什么样，还能读到当时为什么改。而且它有一样纸永远做不到的东西：一张平行的页面，让你在不碰当前可用版本的前提下试危险的想法。

版本控制系统。记录每次改动，支持分支与合并。

GitHub the shared shelf共享的书架

Where the whole team's notebooks live, plus the peer-review step: before your pages join the official record, a colleague reads them and comments in the margin. That review is called a pull request.

A hosting platform for Git repositories, with reviews, issues and automation.

全组的记录本都放在这里，外加一道同行评议：在你的页面并入正式记录之前，同事会读一遍并在旁边写批注。这道评议就叫 Pull Request。

托管 Git 仓库的平台，附带评审、议题追踪和自动化。

Open source开源 a published protocol公开发表的方案

A method published with the full recipe attached. Anyone can read it, check it, improve it, and catch your mistake. The closed alternative is a black-box kit: often excellent, but you take its word for everything, and if the vendor stops making it you are stranded.

Software whose source code is public and licensed for reuse — Python, Linux, pandas, Postgres.

一份把完整配方一起发表出来的方法。任何人都能读、能验、能改进，也能指出你的错。闭源那条路是黑盒试剂盒：常常很好用，但一切都只能听它的，而且供应商一停产你就被困住。

源代码公开、并授权他人使用的软件 —— Python、Linux、pandas、Postgres。

Cloud云 the shared facility共享平台

Somebody else's building, full of machines, rented by the minute. You stop owning the mass spectrometer and start paying per run. There is no cloud — there is only someone else's computer, in a very well air-conditioned room.

AWS, Azure, GCP — compute, storage and networking rented on demand.

别人的一栋楼，里面全是机器，按分钟出租。你不再拥有那台质谱仪，而是按次付费。世上没有"云"——只有别人的电脑，放在一间空调开得很好的房间里。

AWS、Azure、GCP —— 按需租用的算力、存储和网络。

Server服务器 a computer that never sleeps一台永不睡觉的电脑

Physically the same kind of machine as your laptop. The only difference is that it stays on, sits in a room with good cooling, and waits for other computers to ask it for things. That's it. That's the whole mystery.

A machine (or virtual machine) running software that responds to network requests.

物理上和你的笔记本是同一类机器。唯一的区别是它一直开着、待在散热良好的房间里、等着其他电脑来问它要东西。就这样。全部的神秘感就到此为止。

一台（或一台虚拟的）机器，运行着响应网络请求的软件。

ETL sample prep样本前处理

Collect the raw material, clean and standardise it, store the finished preparation where everyone can find it. Exactly what you do before an assay — just at industrial scale and on a schedule.

Extract, Transform, Load — the pipeline that moves data from sources into a warehouse.

采集原料、清洗并标准化、把处理好的成品存到大家都能找到的地方。和你做检测前的准备一模一样——只是工业规模，而且按时自动跑。

抽取、转换、加载 —— 把数据从源系统搬进数据仓库的管道。

The terminal — how computers actually work终端 —— 电脑其实是怎么运作的

This is the single biggest gap between someone who uses a computer and someone who works on one. It is also much simpler than it looks.这是"用电脑的人"和"在电脑上工作的人"之间最大的一道鸿沟。而它其实比看起来简单得多。

🧪 The instrument has a screen. It also has a keypad.🧪 仪器有屏幕，也有键盘。

Think of a lab instrument with a nice touchscreen: tap Run, tap Export. Lovely for one sample. Now imagine the supervisor says: run all 400 samples overnight, with three different settings, and log every result.

You cannot tap that. But the same instrument has a command port where you can send it typed instructions — and those can be written down, repeated, scheduled and reviewed. The touchscreen is the GUI. The command port is the CLI. They drive the same machine.

想象一台带漂亮触摸屏的实验仪器：点运行、点导出。做一份样本很舒服。现在主管说：今晚把 400 份样本全跑完，用三种不同参数，每个结果都要记录。

这个你点不出来。但同一台仪器还有一个命令端口，可以给它发送打字指令——而那些指令是可以被写下来、重复、定时、审阅的。触摸屏就是 GUI，命令端口就是 CLI。它们驱动的是同一台机器。

Why is there a black window with text in it?为什么会有一个黑底白字的窗口？

Here is the fact that reframes everything: the graphical interface came second. Computers were text-driven first, for about twenty years, and they still are underneath. The desktop, the icons, the drag-and-drop — all of it is a friendly skin painted on top, added because humans are much better at pointing than at remembering.

When you drag a file into a folder, something underneath runs the equivalent of mv report.csv archive/. When you click Install, something runs a package command. The GUI never gained a power the CLI didn't have — it just hid the words.

And it hid them at a price. A click cannot be saved, repeated, emailed, version-controlled, scheduled at 2am, or explained to a colleague. A typed command is all of those things by default, because it is just text. That is the entire reason professionals live in the terminal.

有一个事实能把一切重新框住：图形界面是后来才有的。电脑最早的二十来年是纯文字驱动的，而在底层，它到今天仍然是。桌面、图标、拖拽——全都是后来刷在上面的一层友好外皮，因为人类"指"比"记"厉害得多。

你把文件拖进文件夹时，底下运行的其实相当于 mv report.csv archive/。你点"安装"时，底下运行的是一条包管理命令。GUI 从未获得 CLI 没有的能力——它只是把那些字藏起来了。

而且藏得有代价。一次点击没法保存、没法重复、没法用邮件发给别人、没法进版本控制、没法安排在凌晨两点执行、也没法讲给同事听。一条打出来的命令天生就具备以上所有能力，因为它就是文本。这就是专业人士为什么住在终端里的全部原因。

The thing to internalise: the CLI is not the "old" way and the GUI the "new" way. They are two doors into the same house, and the text door is the one that leads to every room.需要内化的一点：CLI 不是"旧办法"、GUI 不是"新办法"。它们是通往同一栋房子的两扇门，而文字那扇门通向每一个房间。

Linux is an operating system — the same category of thing as Windows or macOS. It is the referee that shares one machine between many programs (floor 08 of the tower at the end of this guide).

Two things make it different, and both matter to you:

1. It is free and open. Anyone can read it, run it, copy it, modify it, and put it on a million machines without asking permission or paying a licence.

2. It does not need a screen. It runs perfectly happily with no monitor, no mouse, no desktop — because it was designed text-first. That is exactly what a server needs.

Which is why the overwhelming majority of servers on earth run Linux. Every cloud instance you will ever launch, almost every database, almost every container, the machines behind Google, Netflix, Grab, your bank, and the one that served you this page. Your Android phone is Linux underneath too.

What this means practically: when you connect to a server, there is nothing to click. A prompt appears and waits. Learning about twenty commands is what turns that from terrifying into ordinary — and it is genuinely about twenty.

Linux 是一个操作系统——和 Windows、macOS 属于同一类东西。它是那个让很多程序共用一台机器的裁判（也就是本指南最后那座塔的第 08 层）。

它有两点不同，而这两点对你都很重要：

1. 它免费且开放。任何人都能读它、跑它、复制它、改它，装到一百万台机器上也不用申请许可、不用付授权费。

2. 它不需要屏幕。没有显示器、没有鼠标、没有桌面，它照样跑得很开心——因为它从设计之初就是文字优先的。而这正是服务器需要的。

所以地球上绝大多数服务器跑的都是 Linux。你将来启动的每一个云实例、几乎每一个数据库、几乎每一个容器，谷歌、Netflix、Grab、你的银行背后的机器，以及把这个页面发给你的那台，都是。你的安卓手机底下也是 Linux。

实际意味着什么：当你连上一台服务器，没有任何东西可以点。一个提示符出现，然后等着你。学会大约二十条命令，就能把"可怕"变成"平常"——而且真的就是二十条左右。

This is worth understanding, because it changes how you should work for the next few years.

AI models are unusually strong at the command line, and the reason is structural: a model is a text engine, and the CLI is a world made entirely of text. The command is text. The output is text. The error message is text. So the model can read the result of its own action and decide the next one — a loop that simply does not exist when the interface is a button somebody has to click.

There is a second reason. Commands are composable: small tools that each do one thing, joined with a pipe | so one tool's output becomes the next one's input. That is a tiny, regular grammar — exactly the kind of structure a language model handles well, and exactly the kind of thing that is tedious for a human to remember.

So the practical shape of the next few years: you decide what needs to happen and whether the result is right; the model writes the incantation. "Find every CSV in this folder modified in the last 3 days, count the FAIL rows in each, and write a summary" is a sentence you can now say out loud and get a correct command for.

The catch, and it is a real one: commands are irreversible in a way clicking usually isn't. There is no undo and no recycle bin. So the discipline is simple and non-negotiable — read every command before you run it, and never run one you can't explain. Especially anything with rm, sudo, or a redirect > in it.

这一点值得理解，因为它会改变你未来几年的工作方式。

AI 模型在命令行上强得异常，而原因是结构性的：模型是一台文本引擎，而 CLI 是一个完全由文本构成的世界。命令是文本，输出是文本，报错也是文本。于是模型可以读到自己这一步的结果，再决定下一步——而当界面是"一个需要人去点的按钮"时，这个循环根本不存在。

还有第二个原因。命令是可组合的：一堆各自只做一件事的小工具，用管道 | 串起来，让前一个的输出变成后一个的输入。这是一套极小而规整的语法——恰好是语言模型最擅长的结构，也恰好是人类最懒得背的东西。

所以未来几年的实际形态是：你决定要发生什么、以及结果对不对；模型来写那句咒语。"找出这个文件夹里最近 3 天修改过的所有 CSV，数一下每个里面有多少 FAIL 行，写个汇总"——这句话你现在可以直接说出来，然后拿到一条正确的命令。

但有个真实的代价：命令的不可逆程度是点击通常没有的。没有撤销，也没有回收站。所以纪律很简单，而且没得商量——运行前把每条命令读一遍，永远不要运行你解释不了的命令。尤其是带 rm、sudo 或重定向 > 的。

  • Backend is the part you cannot see. It runs on someone else's computer and holds the rules.

🧪 The lab analogy🧪 实验室类比

1Frontend fundamentals — HTML, CSS, JavaScript前端基础 —— HTML、CSS、JavaScript

Why does the frontend exist at all?为什么会有"前端"这个东西？

Because a computer's data is unreadable to a human. A database row is ("S-001",0.98,1,"2026-03-14"). A person needs a heading, a colour, a button, an ordering. The frontend exists purely to translate machine truth into human understanding — and to translate human intent (a click, a typed number) back into something the machine can act on.

Its purpose in one line: it is the negotiating layer between a system that only understands structure and a person who only understands meaning.

因为电脑里的数据人是读不懂的。数据库里一行记录长这样：("S-001",0.98,1,"2026-03-14")。而人需要标题、颜色、按钮、排序。前端存在的唯一目的，就是把机器的事实翻译成人能理解的东西——再把人的意图（一次点击、输入的一个数字）翻译回机器能执行的指令。

一句话说清它的目的：它是"只懂结构的系统"和"只懂意义的人"之间的谈判层。

How it used to work以前是怎么做的
  • Every click sent a request to the server, which sent back a whole new page. The screen went white and reloaded.
  • HTML, styling and behaviour were tangled in one file — <font color="red"> sat right in the content.
  • A different page had to be hand-written for every combination of data.
  • 每点一次，浏览器就向服务器要一整个新页面，屏幕闪白、整页刷新。
  • 结构、样式、行为全混在一个文件里——<font color="red"> 直接写在内容中间。
  • 数据有多少种组合，就得手写多少个页面。
→
How it works now现在是怎么做的
  • The page loads once. JavaScript fetches only the data that changed and redraws just that part.
  • Strict separation: HTML = structure, CSS = appearance, JS = behaviour. Change the colour scheme without touching the content.
  • One template + data renders a thousand different views.
  • 页面只加载一次，JavaScript 只去取变化的数据，然后局部重绘那一小块。
  • 严格分工：HTML 管结构，CSS 管外观，JS 管行为。改配色不用碰内容。
  • 一套模板加上数据，就能渲染出上千种不同的视图。

Why the change happened: networks stayed slow while screens got more interactive. Sending 2 KB of JSON instead of a 200 KB page is a hundred-fold saving, repeated on every single click.

为什么会这样演进：网络速度没跟上，但界面越来越需要交互。每次点击传 2 KB 的 JSON 而不是 200 KB 的整页，就是一百倍的节省，而且每点一次都省一次。

Three languages, three jobs, and they never overlap. HTML is the structure. CSS is the appearance. JavaScript is the behaviour.

三种语言，三份工作，互不越界。HTML 管结构，CSS 管外观，JavaScript 管行为。

🧪 Think of a conference poster🧪 想象一张学术海报

HTML is the content you wrote — title, sections, the figure, the references. CSS is the layout and design — font sizes, colour scheme, where the figure sits. JavaScript is what happens when someone walks up and interacts — a slider that changes the plot, a button that reveals raw data. Take CSS away and your poster is still readable, just ugly. Take HTML away and there is nothing to style.

HTML 是你写的内容——标题、章节、图、参考文献。CSS 是排版和设计——字号、配色、图放在哪。JavaScript 是有人走过来跟它互动时发生的事——拖动滑块图就变、点按钮显示原始数据。去掉 CSS，海报还能读，只是难看；去掉 HTML，就没有东西可以被美化了。

How deep should you go? As a data engineer: shallow, but real. Read a page's HTML, know what a <div> is, write ten lines of JavaScript. You do not need to master CSS layout. Two weekends is enough.

该学到多深？作为数据工程师：浅，但要真懂。能读懂一个页面的 HTML、知道 <div> 是什么、能写十行 JavaScript 就够了。你不需要精通 CSS 布局。两个周末足够。

If you never learn any frontend: you can still do the job — but you become dependent. When a dashboard shows a wrong number, you won't be able to tell whether your pipeline sent bad data or the page displayed good data badly. That's a whole class of bug you cannot debug alone, and you'll be waiting on someone else's calendar to find out.

The other failure mode: designing an API without knowing how it will be consumed. You'll return data in a shape that forces the frontend to do ten transformations, and they'll quietly stop asking you for things.

Why is there a "backend" separate from the page?为什么要有一个和页面分开的"后端"？

Three reasons, and they're all about trust.

1. You cannot trust the browser. Anything running on a user's machine can be edited by that user. If the price check happens in JavaScript, a determined person changes the price to zero. Rules that matter must run somewhere the user cannot reach.

2. You cannot ship the data. The browser can't hold ten million rows, and you wouldn't want it to — it would mean handing every user the entire database.

3. One truth, many screens. The web app, the mobile app and the nightly report must all apply the same QC rule. Write it once in the backend, and all three get the same answer forever.

三个原因，而且全都关于信任。

1. 浏览器不可信。任何跑在用户机器上的东西，用户都能改。如果价格校验写在 JavaScript 里，有心人把价格改成 0 就行。真正重要的规则必须跑在用户碰不到的地方。

3. 一份真相，多个屏幕。网页、手机 App、每晚的报表，必须用同一条 QC 规则。在后端写一次，这三个地方永远得到同一个答案。

3Databases — SQL and relational tables数据库 —— SQL 与关系表

This is the single most valuable skill in your job. If you learn only one thing exceptionally well this year, make it SQL.

这是你这份工作里最值钱的一项技能。如果这一年只能把一件事学到出类拔萃，就选 SQL。

Why split data into separate tables at all?为什么非要把数据拆成好几张表？

Because the same fact stored twice will eventually disagree with itself. That is not a risk — it is a certainty, and it's the reason the entire relational model exists.

Imagine one giant sheet where every row repeats a patient's full name, address and date of birth for every test they ever had. Change one address and you must find twelve rows. Miss one, and your data now contains two different truths about the same person. Six months later nobody knows which is right.

The purpose in one line: store each fact exactly once, in exactly one place, so there is only ever one version of the truth to correct.

因为同一个事实存两遍，迟早会自己跟自己矛盾。这不是"有风险"，这是必然，也是整个关系模型存在的理由。

想象一张巨大的表，病人每做一次检测，就重复记一遍他的全名、地址、出生日期。地址改一次，你得找出十二行来改。漏掉一行，你的数据里就有了关于同一个人的两个版本。半年后，没人知道哪个是对的。

一句话说清目的：每个事实只存一次、只存一处，这样需要更正时永远只有一个版本。

How it used to work以前是怎么做的
  • Data lived in flat files, one giant file per topic, with everything repeated on every line.
  • To answer a question you wrote a whole program that read the file top to bottom.
  • Two people writing at once corrupted the file. There was no such thing as a safe concurrent update.
  • Changing the format meant rewriting every program that read it.
  • 数据存在平面文件里，一个主题一个大文件，每一行都把所有信息重复一遍。
  • 想回答一个问题，就得写一整个程序把文件从头读到尾。
  • 两个人同时写就会把文件写坏。当时根本没有"安全并发更新"这回事。
  • 格式一改，所有读它的程序都得重写。
→
How it works now现在是怎么做的
  • Data lives in related tables. Each fact once; keys point between them.
  • You describe what you want in SQL. The database figures out how to get it — and it's better at that than you are.
  • Thousands of people write at once safely. Transactions guarantee all-or-nothing.
  • Add a column without breaking a single existing query.
  • 数据存在互相关联的表里。每个事实只存一次，靠"键"互相指向。
  • 你用 SQL 描述要什么，数据库自己决定怎么取——而且它比你更擅长这件事。
  • 成千上万人同时写也安全。事务保证要么全成、要么全不成。
  • 加一列，不会弄坏任何一条已有的查询。

And the newest layer: for analytics, tables are now often stored by column instead of by row (BigQuery, Snowflake, DuckDB, Parquet files). Asking for the average of one column no longer means reading all forty. Same relational idea — different physical layout, ten to a hundred times faster for the questions analysts actually ask.

还有最新的一层：做分析时，表现在常常按列存储而不是按行（BigQuery、Snowflake、DuckDB、Parquet 文件）。求某一列的平均值，不再需要把四十列全读一遍。关系模型没变——只是物理存储方式变了，对分析师真正会问的那类问题，快十倍到一百倍。

One table for patients, one table for tests. The test table stores only a small patient_id pointing back. SELECT p.name, p.city, t.test_name, t.value
FROM patients AS p
JOIN tests AS t
  ON t.patient_id = p.patient_id;
-- How many tests per city, worst first? / 各城市检测数与均值，最差的排前面
SELECT p.city, COUNT(*) AS n_tests, AVG(t.value) AS avg_value
FROM patients AS p
JOIN tests AS t ON t.patient_id = p.patient_id
WHERE t.test_name = 'Glucose'
GROUP BY p.city
HAVING COUNT(*) > 5
ORDER BY avg_value DESC;

# 就解决了 90% 的 SQL 困惑。

  1. FROM / JOIN   # get and combine tables / 取表并拼接
  2. WHERE          # throw away rows / 扔掉不要的行
  3. GROUP BY       # bucket what's left / 把剩下的分组
  4. HAVING         # throw away whole buckets / 扔掉整组
  5. SELECT         # pick columns / 选列、算值
  6. ORDER BY       # sort / 排序
  7. LIMIT          # cut / 截断

# SELECT: SELECT hasn't run yet.
# 这就是为什么 WHERE 用不了你在 SELECT 里起的别名——
# 那时候 SELECT 还没执行。

If you keep everything in one wide table: updates become unsafe. A single spelling correction has to be applied in a hundred places, and the day someone applies it in ninety-nine, your data has quietly forked.

If you avoid SQL and pull everything into Python instead: you move a million rows across the network to compute a number the database could have computed in place in 40 milliseconds. It works at 10,000 rows and collapses at 10 million — and it will collapse in production, not in testing.

The subtle one: without knowing the execution order, you'll write a WHERE that silently turns your LEFT JOIN into an inner join and quietly deletes the exact rows you were investigating.

如果把所有东西塞进一张宽表：更新会变得不安全。改一个拼写要在一百处同步，而当有人只改了九十九处那天，你的数据就悄悄分叉了。

如果绕开 SQL、把数据全拉到 Python 里算：你为了算一个数字，把一百万行搬过网络，而数据库原地 40 毫秒就能算完。一万行时没问题，一千万行时崩掉——而且是在生产环境崩，不是在测试环境。

还有个隐蔽的：不懂执行顺序，你写的 WHERE 会悄悄把 LEFT JOIN 变成内连接，把你正要调查的那些行恰好过滤掉。

Why do systems talk through an API instead of just sharing the database?为什么系统之间要走 API，而不是直接共用数据库？

            
Because a shared database is a shared fate. If ten applications read your tables directly, you can never rename a column again — you'd break all ten, and you don't even know who they are.

            
An API is a promise with a boundary: "you may ask me these specific questions, in this specific way, and I promise this specific shape of answer." Behind that boundary you are free to restructure everything. That freedom is the entire product.

            
The second reason is permission. Direct database access is all-or-nothing. An API can decide, per request, that this caller may see their own samples and not anyone else's.

            
因为共用数据库等于共担命运。如果十个应用直接读你的表，你就再也别想给某一列改名了——十个全会崩，而且你连它们是谁都不知道。

            
API 是一个带边界的承诺："你可以用这种方式问我这些特定的问题，我保证给你这种特定形状的答案。"边界背后，你想怎么重构都行。这份自由本身就是它的全部价值。

            
第二个原因是权限。直连数据库是全有或全无；API 可以针对每一次请求判断：这个调用方只能看自己的样本，看不到别人的。

  • Every caller identifies itself with a token that can be revoked in one click.

2Version control — Git and GitHub版本控制 —— Git 与 GitHub


        

          

            
            
            
            
          

          

            
Why does code need a notebook?为什么代码需要一本记录本？

            
Three questions come up constantly, and without version control none of them have answers:

            
"When did this break?" — you need to compare today's code with a version that worked.

            "Why is this line here?" — you need the reasoning of the person who wrote it, eight months ago, who may have left.

            "Can we undo it?" — you need to go back without losing everything that came after.

            
The purpose in one line: Git makes every change reversible, attributable and explainable — which is exactly what a lab notebook does for an experiment, and for exactly the same reason.

            
有三个问题会反复出现，而没有版本控制，它们一个都答不上来：

            
"这是什么时候坏的？"——你需要把今天的代码和一个能跑的版本对比。

            "这行为什么在这？"——你需要八个月前写它那个人的理由，而那人可能已经离职了。

            "能撤回吗？"——你需要退回去，同时不丢掉之后做的所有东西。

            
一句话说清目的：Git 让每一次改动都可撤销、可追责、可解释——这正是实验记录本对实验做的事，理由也完全一样。

          

          

            

              
How it used to work以前是怎么做的

                
  • report_v2_final_FINAL_usethis.py. Seven copies of a folder, and nobody sure which one is live.
  • Two people editing the same file meant one person's work silently vanished.
  • History lived in email threads, or in one person's memory.
  • "Who changed this and why?" was usually unanswerable.

                
  • report_v2_final_FINAL_usethis.py。同一个文件夹七个副本，没人确定哪个在跑。
  • 两个人改同一个文件，其中一个人的工作就无声消失了。
  • 历史记录存在邮件线程里，或者某个人的记忆里。
  • "这是谁改的、为什么改？"通常答不上来。

              
→

              
How it works now现在是怎么做的

                
  • One folder. Every version ever, retrievable, with dates and authors.
  • Parallel branches let ten people work at once without touching each other's files.
  • Every change carries a written reason, permanently attached.
  • Pull requests mean a second person reads it before it reaches production — peer review for code.

                
  • 一个文件夹。历史上每一个版本都能取回，带日期和作者。
  • 并行的分支让十个人同时干活，互不碰对方的文件。
  • 每次改动都带一段书面理由，永久附在上面。
  • Pull Request 意味着上线前有第二个人读过——代码版的同行评议。

            

            
Where it's heading: Git is now the trigger for everything else. Push a branch and tests run automatically; merge it and it deploys itself. The commit isn't just a record any more — it's the button that starts the machine.

            
它正在往哪走：Git 现在是一切的触发器。推一个分支，测试自动跑；合并进去，它自己就上线了。提交不再只是记录——它是启动整台机器的那个按钮。

Throw the branch away. Works? Merge it back.

              
一本合格的实验记录本：有日期、有签名、从不涂改。Git 就是代码版的它。而且它有一件纸质记录本永远做不到的事：你可以开一条分支——一份平行副本，在上面试危险的新方案，完全不碰当前能用的版本。失败？丢掉分支。成功？合并回去。

Why would anyone give away code — and why should you care?为什么有人白送代码 —— 你为什么该在意？

            
Because software has almost zero copying cost, and a tool used by a million people gets debugged by a million people. Giving it away is often the fastest route to a tool that actually works.

            
For you, the reason to care is verifiability. Open source is a published protocol with the full recipe attached — you can read it, test it, and know exactly what it does to your data. Closed software is a black-box kit: often excellent, but you take its word for it, and if the vendor discontinues it you are stranded.

            
因为软件的复制成本几乎为零，而一个被一百万人使用的工具会被一百万人调试。白送出去，往往是让工具真正可用的最快路径。

            
对你来说，值得在意的理由是可验证性。开源就是一份连完整配方一起发表的方案——你能读它、测它，确切知道它对你的数据做了什么。闭源软件是一个黑盒试剂盒：常常很好用，但你只能信它的说法，而且供应商一停产你就被困住了。

  • A bug meant filing a ticket and waiting for the next quarterly release.
  • Vendor lock-in was the business model, and price rises were unarguable.
  • AI models, similarly, were entirely behind an API — rent only.

  • 发现 bug 就提工单，然后等下一个季度版本。
  • 供应商锁定就是商业模式，涨价你也没得谈。
  • AI 模型同理，完全藏在 API 后面——只能租。

  • Companies fund the projects they depend on, because the alternative is maintaining a fork alone.

1What an LLM actually is大模型到底是什么


        

          

            
            
            
            
          

          

            
Why does understanding the mechanism matter, if you can just use it?既然会用就行，为什么还要懂它的原理？

            
Because the mechanism explains every strength and every failure. A model does one thing: predict the most likely next chunk of text, over and over, extremely well.

            
From that one sentence, everything follows. Why is it so good at boilerplate? Because boilerplate is highly predictable. Why does it invent a column name that doesn't exist? Because sample_purity_pct is what usually comes next in text like yours — and the model has no way to check. Why does a wrong answer sound exactly as confident as a right one? Because confidence isn't computed separately; it's generated the same way the content is.

            
The purpose of knowing this: it tells you precisely where to look for errors, instead of trusting or distrusting the whole thing at random.

            
因为原理解释了它的每一项长处和每一种失败。模型只做一件事：一次又一次地预测最可能的下一段文字，而且做得极好。

            
从这一句话，一切都能推出来。为什么它写样板代码那么强？因为样板代码高度可预测。为什么它会编出一个不存在的列名？因为在类似你这样的文本里，接下来通常就是 sample_purity_pct——而模型没有任何办法去核实。为什么错误答案听起来和正确答案一样笃定？因为"笃定"不是单独算出来的，它和内容是同一套机制生成的。

            
知道这个的用处：它精确地告诉你该去哪里找错，而不是凭感觉整体相信或整体怀疑。

          

          

            

              
How software used to be built以前软件是怎么造的

                
  • Every behaviour had to be written as an explicit rule by a human. "If purity < 0.95 then fail."
  • Anything fuzzy — reading a messy address, summarising a document — was effectively impossible.
  • Adding a language, a format or an edge case meant a new project.
  • Search meant matching keywords. If you used a different word, you found nothing.

                
  • 每一种行为都得由人写成明确的规则。"如果纯度 < 0.95 就判不合格。"
  • 任何模糊的事——读一个乱写的地址、给文档做摘要——基本不可能。
  • 多支持一种语言、一种格式、一个边缘情况，就是一个新项目。
  • 搜索靠关键词匹配。换个说法就什么都搜不到。

              
→

              
How it works now现在是怎么做的

                
  • You describe the outcome in plain language and the model produces a first attempt.
  • Fuzzy tasks became routine: extract fields from a scanned invoice, summarise 200 tickets, translate a script from R to Python.
  • The bottleneck moved from writing code to verifying it — which is where your judgment now earns its keep.
  • Search works by meaning, not by matching characters.

                
  • 你用大白话描述想要的结果，模型给出第一版尝试。
  • 模糊任务变成了日常：从扫描发票里抽字段、给 200 张工单做摘要、把 R 脚本翻译成 Python。
  • 瓶颈从写代码变成了验代码——而这正是你的判断力开始值钱的地方。
  • 搜索按含义匹配，而不是按字符匹配。

            

            
What did NOT change: the model still cannot know whether it's right. Everything about verification, testing, data quality and security got more important, not less — because code now arrives faster than anyone can read it.

            
没有变的是：模型依然无法知道自己对不对。验证、测试、数据质量、安全这些事变得更重要而不是更不重要——因为现在代码产生的速度已经超过任何人阅读的速度。

They answer any question fluently and confidently. Sometimes the fluent answer is wrong, and it sounds exactly as confident as the right one.

              
想象一个人，几乎读过有史以来所有论文、手册和论坛帖子，对"下一句通常是什么"有极好的直觉——但一次实验都没做过。他能流畅、笃定地回答任何问题。有时候那个流畅的答案是错的，而且听起来和对的一样笃定。

If you treat it as a search engine: you'll assume it retrieved a fact when it actually composed one. Search engines return documents that exist; a model returns text that is likely. These are completely different guarantees.

              
If you treat it as a calculator: you'll trust arithmetic it did in prose. Ask it to write the code that computes the number instead — code you can run and check.

              
If you never verify: the failure is not that you'll be wrong occasionally. It's that you'll be wrong confidently and at scale, having shipped a plausible answer into a report that people made decisions on.

              
如果把它当搜索引擎：你会以为它"查到"了一个事实，其实它是"编"了一个。搜索引擎返回存在的文档，模型返回可能的文本。这是完全不同的保证。

              
如果把它当计算器：你会相信它在行文中做的算术。应该让它写出计算这个数字的代码——你能跑、能验的代码。

              
如果从不验证：问题不是你偶尔会错，而是你会笃定地、成规模地错——把一个看起来很合理的答案发进了别人据以做决策的报表里。

Treat every output the way you'd treat a promising result from a single unreplicated run — interesting, worth checking, never publishable on its own. Run the code. Check the number. 能保住你职业生涯的一条规矩：大模型产出的是看起来合理的东西，不是已验证的东西。对待每一个输出，就像对待一次未重复实验得到的漂亮结果——有意思、值得查、但绝不能单独发表。跑一遍代码、核一遍数字、读一遍原始出处。

        

      


      
      

        
2Prompt engineering — writing a good protocol提示词工程 —— 写一份好的操作方案


        

          

            
            
            
            
          

          

            
Why does phrasing change the answer so much?为什么换个说法，答案差这么多？

            
Because the model can only use what's in front of it. It cannot see your screen, your schema, your team's conventions, or the thing you decided last Tuesday. Every ambiguity you leave open, it must fill with the statistically most common assumption — which is usually not yours.

            
The purpose in one line: a prompt is a briefing. Most bad answers are not stupid models; they are starved briefings.

            
因为模型只能用它眼前有的东西。它看不到你的屏幕、你的表结构、你团队的惯例，也不知道你上周二定了什么。你留下的每一处模糊，它都必须用统计上最常见的假设去填——而那通常不是你的假设。

            
一句话说清目的：提示词是一份任务简报。大部分糟糕的答案不是因为模型笨，而是因为简报太饿。

  • Chained tricks to get JSON out reliably; often it came back malformed.
  • Prompts were personal folklore, passed around as screenshots.

  • 上下文窗口很小，什么都得压缩，然后祈祷。
  • 要靠一连串技巧才能稳定拿到 JSON，而且常常格式还是坏的。
  • 提示词是个人经验，靠截图在群里流传。

              
→

  • Plain, specific, structured instructions. The superstition mostly stopped working and stopped being needed.
  • Long context: paste the whole schema, the whole error, the whole file.
  • Structured output is a first-class feature — you define the shape, you get that shape.
  • Good prompts live in Git as reusable files, reviewed like code.

                
  • 朴素、具体、有结构的指令。咒语基本失效，也不再需要。
  • 长上下文：整个表结构、整段报错、整个文件，直接贴进去。
  • 结构化输出成了一等功能——你定义形状，就得到那个形状。
  • 好的提示词像代码一样存进 Git、可复用、可评审。

            

            
What this means: "prompt engineering" is becoming ordinary technical writing — say precisely what you want, for a reader with no context. That skill was always valuable. Now it's compensated.

            
这意味着："提示词工程"正在变成普通的技术写作——把你要什么说清楚，写给一个毫无背景的读者看。这项能力一直都值钱，现在只是终于被付钱了。

◈ Real-world example◈ 真实场景

          
You need to classify 4,000 free-text maintenance complaints into eight categories.

          
Vague prompt: "categorise these." You get eleven categories, inconsistent naming, and prose around each answer that breaks your parser. Useless for a pipeline.
Real prompt: list the eight allowed categories verbatim, give two worked examples including one ambiguous case, specify {"id":..., "category":..., "confidence":...} as the only output, and add "if it fits none, return OTHER — do not invent a category." Now it runs unattended over 4,000 rows, and the confidence field tells you which 60 need a human. The second prompt took eight minutes longer to write and turned a demo into a system.

          
你需要把 4000 条自由文本的维修投诉分成八类。

真正的提示词：把八个允许的类别原样列出，给两个示例（其中一个是边界情况），指定唯一输出为 {"id":..., "category":..., "confidence":...}，并加上"如果都不符合，返回 OTHER——不要自己造类别"。现在它能无人值守跑完 4000 行，而 confidence 字段会告诉你哪 60 条需要人看。第二版只多花了八分钟去写，却把一个演示变成了一套系统。

Because context is everything, and a chat window has none of yours. Paste a function into a chat and the model must guess your file layout, your naming conventions, your database schema and which library version you're on.

            
An editor like Cursor can read the repository. Ask "why is this pipeline dropping rows?" and it can actually go and look at the transform, the schema and the tests. The purpose in one line: move the model from guessing about your code to reading it.

            
因为上下文就是一切，而聊天窗口对你的上下文一无所知。把一个函数粘进聊天框，模型只能猜你的文件结构、命名习惯、数据库表结构，以及你用的是哪个版本的库。

How coding used to go以前写代码是怎样

  • Boilerplate typed by hand, every time, with typos.
  • Tests written last, badly, or not at all.
  • Understanding a stranger's 800-line file took a full day.

                
  • 遇到陌生报错 → 搜索 → 开九个标签页 → 找到一个 2016 年针对旧版本的答案。
  • 样板代码每次都手敲，每次都有拼写错误。
  • 测试最后写、写得差，或者干脆不写。
  • 看懂别人写的 800 行文件要花一整天。

              
→

  • Paste the error with the file — get an explanation grounded in your actual code.
  • Boilerplate is generated in seconds; you review instead of type.
  • Tests get written because the cost of writing them collapsed.
  • That 800-line file gets explained function by function in ten minutes.

                
  • 把报错连同文件一起给它——得到基于你真实代码的解释。
  • 样板代码几秒生成，你从"敲"变成"审"。
  • 测试终于写了，因为写测试的成本塌下来了。
  • 那个 800 行的文件，十分钟就能被逐个函数讲清楚。

            

            
The honest trade-off: the cost of producing code fell much faster than the cost of understanding it. Teams that don't adjust end up with more code than anyone has read. Review discipline is now the scarce skill.

            
诚实的取舍：产出代码的成本下降得比理解代码的成本快得多。不做调整的团队，最后会拥有比任何人读过的都多的代码。评审的纪律，才是现在稀缺的能力。

A lab partner who can set up any apparatus in seconds but has no idea what you're trying to prove. Delegate the tedium — boilerplate, renaming, writing tests, translating R to Python. Never delegate the decision about whether the result is correct.

              
一个几秒钟就能搭好任何装置、但完全不知道你想证明什么的实验搭档。把繁琐的部分交出去——样板代码、批量改名、写测试、把 R 翻成 Python。永远不要把"结果对不对"的判断交出去。

Explaining unfamiliar code line by line. Writing tests. Converting between languages. Generating boilerplate. First-draft documentation. Suggesting what might be causing an error.

                
逐行解释陌生代码；写测试；语言之间转换；生成样板代码；文档初稿；给出报错可能的原因。

              
Dangerous uses危险的用法

                
Accepting a 200-line diff you haven't read. Letting it design your data model. Trusting a number it produced. Running its shell commands against production without reading them.

A discipline worth building now: for the first year, before accepting any AI-written block, make yourself explain out loud what each line does. If you can't, don't merge it. The moment you ship code you don't understand, you've made a promise you can't keep at 3am.

              
现在就该养成的纪律：第一年里，接受任何 AI 写的代码块之前，逼自己出声解释每一行在干什么。解释不出来，就别合并。你上线一段自己看不懂的代码那一刻，就许下了一个凌晨三点兑现不了的承诺。

If you use it without reading: far worse. You accumulate code nobody understands — including you. The first outage is unrecoverable in any reasonable time, because debugging requires a mental model you never built.

如果你拒绝用：在机械性工作上，你会比同事慢两到四倍，而这个差距在绩效评估里是看得见的。手敲样板代码没有奖章。

              
如果用了但不读：糟得多。你会积累一堆没人看得懂的代码——包括你自己。第一次故障就无法在合理时间内恢复，因为排查需要一个你从未建立过的心智模型。

              
职业发展版本：只会点"接受"的人，水平会停在起点。每条建议都读一遍、并追问"为什么这么写"的人，学得比以往任何一代都快。同一个工具，两种相反的结局。

            

          

        


        

          
◈ Real-world example◈ 真实场景

          
You inherit a 1,200-line pipeline from someone who left the company. It runs nightly. Nobody knows what half of it does.

          
Old approach: two weeks of careful reading, and you still wouldn't touch it.
New approach: open it in an AI editor and ask, function by function, "what does this do and what would break if I removed it?" Then — and this is the part people skip — verify each claim against the code yourself. It gave you a fast first draft of understanding that you then checked. That distinction is your whole job.

          
你接手了一条 1200 行的管道，原作者已经离职。它每晚都在跑，一半的逻辑没人知道是干嘛的。

          
旧办法：两周仔细阅读，读完你还是不敢动它。

4Agents, MCP, and custom skillsAgent、MCP 与自定义技能


        

          

            
            
            
            
          

          

            
Why does an AI need a protocol to use tools?为什么 AI 用工具还需要一套协议？

            
Because a model that can only talk is limited to what it was trained on. It cannot know today's row count, or whether last night's job succeeded. Give it the ability to run a query and read the result, and it can answer questions about the real world instead of about text.

            
But that ability is dangerous without a boundary. MCP exists so that connection is standard (write it once, any AI client can use it) and scoped (you decide exactly which tools, which tables, read or write).

            
The purpose in one line: it's the difference between an assistant who can advise you and an assistant who can act — with a clearly defined set of keys.

            
因为一个只会说话的模型，被限制在它训练过的内容里。它不可能知道今天的行数，也不知道昨晚的任务有没有成功。给它执行一次查询并读取结果的能力，它就能回答关于真实世界的问题，而不只是关于文本的问题。

            
但这种能力没有边界就很危险。MCP 的存在，是为了让这种连接既标准（写一次，任何 AI 客户端都能用），又受限（你精确决定哪些工具、哪些表、只读还是可写）。

            
一句话说清目的：这是"能给你建议的助手"和"能替你动手的助手"之间的差别——而且钥匙串是明确定义好的。

          

          

            

              
How integration used to work以前的集成是怎么做的

                
  • Every AI tool needed a bespoke integration with every data source. N tools × M systems = N×M pieces of glue code.
  • Permissions were whatever each integration's author happened to implement.
  • You copied data out by hand and pasted it into a chat window — including things you shouldn't have.
  • Nothing was auditable. No log of what the AI actually touched.

                
  • 每个 AI 工具都要为每个数据源写专门的集成。N 个工具 × M 个系统 = N×M 段胶水代码。
  • 权限完全取决于写那个集成的人当时实现了什么。
  • 你手动把数据复制出来粘进聊天框——包括那些本不该复制的。
  • 完全无法审计。AI 到底碰了什么，没有日志。

              
→

              
How it works now现在是怎么做的

                
  • One standard socket. Write an MCP server for your warehouse once; every MCP-compatible client can use it.
  • Permissions live in one place, at the socket — not scattered across integrations.
  • The AI queries live data itself, so nobody pastes a customer list into a chat box.
  • Every tool call is logged. You can answer "what did it touch, and when?"

                
  • 一个标准插口。为你的数仓写一次 MCP 服务，所有兼容 MCP 的客户端都能用。
  • 权限集中在插口这一处——不再散落在各个集成里。
  • AI 自己去查实时数据，没人再把客户名单粘进聊天框。
  • 每次工具调用都有日志。"它碰了什么、什么时候碰的"，你答得上来。

            

          

          

            

              🧪 Giving your assistant keys to the instruments🧪 把仪器的钥匙交给助手
              
An agent is your well-read assistant, now with hands: it can run a query, read a file, call an API, and decide what to do next based on what came back. MCP is the standardised connector — like every instrument in the lab accepting the same plug. A custom skill is your team's written SOP: "when someone asks for the monthly QC report, here's exactly how we do it here, here's the template, here are the gotchas."

              
Agent 就是你那位博览群书的助手，现在有了手：能执行查询、读文件、调 API，并根据返回结果决定下一步。MCP 是标准化的接口——就像实验室里所有仪器都用同一种插头。自定义技能则是你团队写下来的 SOP："有人要月度 QC 报表时，我们这里是这样做的，模板在这，这些坑要注意。"

            

            

              
Security instinct to build early: give an agent the narrowest access that lets it do the job. Read-only beats read-write. One schema beats the whole warehouse. An agent with production write access and a confidently wrong plan is a very fast way to lose data.

              
要早点养成的安全直觉：给 Agent 刚好够用的最小权限。只读优于读写，一个 schema 优于整个数仓。一个有生产写权限、又带着一个自信但错误的计划的 Agent，是丢数据最快的方式。

            

          

          

            

              
If you give an agent broad write access: the first confidently wrong plan does real damage, quickly, and possibly across many tables before anyone notices. Agents act faster than humans can supervise.

              
If you skip the standard and hand-roll integrations: you build N×M glue scripts, each with its own auth handling, each a place where a credential can leak. Replacing one tool means rewriting all of them.

              
If you never write down your team's procedures: every AI-assisted task starts from zero context, and the answers drift. The skill file is what makes the assistant consistent instead of merely fluent.

              
如果给 Agent 宽泛的写权限：第一个自信但错误的计划就会造成真实损失，而且很快，可能在有人发现之前已经波及多张表。Agent 行动的速度超过人类监督的速度。

              
如果不用标准、自己手搓集成：你会写出 N×M 个胶水脚本，每个都有自己的认证处理，每个都是一个可能泄露凭据的地方。换掉一个工具，就得重写全部。

              
如果从不把团队流程写下来：每次 AI 辅助的任务都从零上下文开始，答案会飘。技能文件才是让助手"稳定"而不只是"流畅"的东西。

Every Monday someone spends two hours assembling the same operations report: query three systems, cross-check the numbers, write a summary, post it.

每周一都有人花两小时拼同一份运营报表：查三个系统、对数、写总结、发出去。

          
用 MCP，助手被授予这三个系统的只读权限，外加一份写好的技能文件，说明这份报表到底怎么做——用哪些指标、怎么定义、要标注哪些注意事项。周一早上，它九十秒产出初稿，数字是实时拉的，每个来源都标注了。人读一遍，改掉那一处需要判断的地方，发出去。

Excel is genuinely excellent for looking at data. It is terrible at repeating a process, because there's no record of what you did. Six months later nobody can tell which cells were typed by hand, which were formulas, and which were pasted from somewhere else.

Why not query the source systems directly?为什么不直接查源系统？

            
Four reasons, and each one on its own would justify a pipeline.

            
1. You'd take production down. An analyst's exploratory query on the live order system can lock tables the business needs to take orders.

            2. The shapes don't match. Source systems are built to write one record fast. Analysis needs to read a million records fast. Those are opposite designs.

            3. History disappears. Source systems overwrite. When a customer changes address, last year's report silently changes too — unless someone captured the old value.

            4. Nothing joins. The CRM says "Acme Corp", finance says "ACME Corporation", the shipping system says customer #4471. Someone has to decide those are the same company, once, in one place.

            
四个原因，任何一个单独拿出来都足以支撑建一条管道。

            
1. 你会把生产环境搞挂。分析师在线上订单系统做的探索性查询，可能锁住业务下单要用的表。

            2. 结构对不上。源系统的设计目标是快速写一条记录，分析需要的是快速读一百万条。这是两种相反的设计。

            3. 历史会消失。源系统是覆盖写的。客户改了地址，去年的报表也会悄悄跟着变——除非有人把旧值保存下来。

            4. 拼不起来。CRM 里叫"Acme Corp"，财务系统叫"ACME Corporation"，物流系统叫客户 #4471。得有人在某一处、一次性地判定这是同一家公司。

          

          

            

              
Classic ETL (1990s–2010s)经典 ETL（1990s–2010s）

                
  • Extract → Transform → Load. Transform before loading, because warehouse storage was expensive.
  • Raw data was thrown away after transformation. Got the logic wrong? The original is gone.
  • Built by dragging boxes in a proprietary GUI tool. Not reviewable, not in version control.
  • Ran overnight; you found out about failures the next morning, from a user.

                
  • 抽取 → 转换 → 加载。先转换再入库，因为数仓存储很贵。
  • 转换完原始数据就丢了。逻辑写错了？原件已经没了。
  • 用商业 GUI 工具拖框搭出来，不可评审，不进版本控制。
  • 半夜跑，出问题第二天早上从用户那里才知道。

              
→

              
Modern ELT现代 ELT

                
  • Extract → Load → Transform. Land the raw data first; transform inside the warehouse. Storage got cheap.
  • Raw is kept forever, so you can rebuild everything when a definition changes — and you will.
  • Transformations are SQL files in Git, reviewed in pull requests, tested (dbt).
  • Orchestrators (Airflow, Dagster, Prefect) retry, alert, and show you exactly which step failed.

                
  • 抽取 → 加载 → 转换。先把原始数据落地，再在数仓里转换。因为存储变便宜了。
  • 原始数据永久保留，定义一变就能全量重建——而定义一定会变。
  • 转换逻辑是 Git 里的 SQL 文件，走 PR 评审，有测试（dbt）。
  • 调度器（Airflow、Dagster、Prefect）会重试、告警，并明确告诉你哪一步失败了。

            

            
Why the flip happened: cloud storage costs collapsed while warehouse compute became elastic. Once keeping raw data is nearly free, throwing it away is just risk with no upside. If you learn one modern habit, learn this one: never destroy the raw input.

            
为什么会反转：云存储成本塌了，而数仓算力变成弹性的。一旦保留原始数据几乎免费，丢掉它就只剩风险、没有好处。如果只学一个现代习惯，学这个：永远不要销毁原始输入。

          

          

            

              🧪 Extract, Transform, Load = collect, prep, store🧪 抽取、转换、加载 = 采集、前处理、入库
              
Extract — collect the raw sample from wherever it lives. Transform — the prep bench: clean, standardise units, remove contaminants, derive what you need. Load — store the finished, labelled preparation where everyone can find it.

              
The critical property is the same one your protocols have: reproducibility. Run it twice on the same input, get the same output. If a pipeline can't be re-run safely, it isn't a pipeline — it's a one-off you'll be nervous about forever.

              
抽取——从数据所在的任何地方把原始样本采集过来。转换——前处理台：清洗、统一单位、去除杂质、派生你需要的指标。加载——把处理好、贴好标签的成品存到大家都能找到的地方。

              
最关键的性质和你的实验方案一样：可复现。同样的输入跑两次，得到同样的输出。一条不能安全重跑的管道就不是管道——它只是一次性的东西，你会一直为它提心吊胆。

            

            
The four properties every production pipeline needs生产级管道必须具备的四个性质
              

                
1. Idempotent. Re-running doesn't duplicate or corrupt anything. Rerun-safety is what lets you sleep.

                
2. Observable. It logs what it did, how many rows, how long. When someone asks "did last night's run work?", you should not have to guess.

                
3. Validated. It checks its own output — row counts in range, no nulls in key columns, no impossible values — and fails loudly rather than quietly loading garbage.

                
4. Recoverable. When it fails at 3am (it will), it's obvious where it stopped and safe to restart from there.

                
1. 幂等。重跑不会重复或损坏任何东西。重跑安全，你才睡得着。

                
2. 可观测。它记录自己做了什么、多少行、跑了多久。有人问"昨晚跑成功了吗"，你不该靠猜。

                
3. 有校验。它检查自己的输出——行数在合理范围、关键列无空值、没有不可能的数值——发现问题就大声失败，而不是悄悄写进垃圾数据。

                
4. 可恢复。凌晨三点它挂掉时（一定会），能一眼看出停在哪，并且能安全地从那里重启。

              

            

            

              
Batch vs streaming批处理 vs 流处理

                
Batch runs on a schedule and covers most needs. Streaming processes each event as it arrives. Start with batch. Only go streaming when someone can articulate why minutes-old data isn't good enough.

                
批处理按计划运行，覆盖绝大多数需求。流处理逐条实时处理。先做批处理。只有当有人能说清"为什么几分钟前的数据不够用"时，再上流处理。

              
Tools you'll hear about你会听到的工具

                
Airflow / Dagster / Prefect for scheduling; dbt for SQL transformations; Great Expectations or Soda for validation. Learn the concepts — the tools are interchangeable and will be replaced.

                
Airflow / Dagster / Prefect 做调度；dbt 做 SQL 转换；Great Expectations 或 Soda 做校验。要学的是概念——工具可以互换，也终将被替换。

            

          

          

            

              
If your pipeline isn't idempotent: the first failed-and-rerun night doubles your numbers. Revenue looks like it grew 100%, someone celebrates, and then someone else has to un-celebrate.

              
If it isn't validated: it will happily load a day of zeros because an upstream API returned an error page instead of data. Silence is the worst possible failure mode — an error at least tells you.

              
If it isn't observable: "is the data fresh?" becomes unanswerable, and people stop trusting the whole warehouse. Trust is lost far faster than it's rebuilt.

              
If you transform before loading and throw away raw: the day someone changes the definition of "active customer," you cannot recompute history. You'll have to say "our numbers only go back to today," which is a genuinely painful sentence.

              
如果管道不幂等：第一个"失败后重跑"的夜晚就会让数字翻倍。收入看起来涨了 100%，有人开始庆祝，然后另一个人得去取消庆祝。

              
如果没有校验：上游 API 返回了一个错误页面而不是数据，它会高高兴兴地写进一整天的 0。无声失败是最糟的失败方式——至少报错还会告诉你。

              
如果不可观测："数据是不是最新的？"变成没法回答的问题，然后人们开始不信任整个数仓。信任崩塌的速度远快于重建的速度。

              
如果先转换再加载、还丢掉原始数据：等哪天有人改了"活跃客户"的定义，你没法重算历史。你只能说"我们的数据只能从今天开始"——这是一句真的很难说出口的话。

◈ Real-world example◈ 真实场景

          
The nightly job fails at 02:40 on a network blip. You re-run it at 09:00. By 09:05 the revenue dashboard shows double.

          
The pipeline appended rows instead of replacing them, so yesterday is now in the table twice. Nothing errored — the numbers are simply wrong, and three people have already seen them.
The fix, in order of preference: delete-then-insert for the affected date range, or an upsert keyed on (date, site, sample_id). Both make a re-run a no-op instead of a duplication. The lesson: design for the re-run before the failure — the failure is guaranteed, and it will happen at the least convenient hour.

          
凌晨 2:40 网络抖动导致每晚任务失败。你 9:00 重跑了一次。9:05 收入看板显示的数字翻了一倍。

          
管道是追加而不是替换，所以昨天的数据现在在表里有两份。没有任何报错——数字就是错的，而且已经有三个人看到了。
修复方式，按优先级：对受影响的日期区间先删后插，或者按 (date, site, sample_id) 做 upsert。两者都能让重跑变成"什么都没发生"而不是"翻倍"。教训：在失败之前就为重跑做设计——失败是必然的，而且一定发生在最不方便的时刻。

Why design the tables before you fill them?为什么要在装满之前先设计好表？

            
Because a table's shape decides which questions are cheap and which are impossible. Get it right and "pass rate by region by quarter for instruments overdue for calibration" is one join. Get it wrong and the same question needs a week and a apologetic email.

            
And unlike code, data models are extremely hard to change later — because by then a hundred queries, five dashboards and someone's bonus calculation all depend on the shape you chose.

            
The purpose in one line: decide the shape while it's still free to decide.

            
因为表的形状决定了哪些问题是廉价的、哪些是不可能的。设计对了，"按区域、按季度、只看超期未校准的仪器的合格率"就是一次连接。设计错了，同样的问题要花一周，外加一封道歉邮件。

            
而且和代码不同，数据模型后期极难修改——因为到那时，一百条查询、五个看板、还有某人的奖金计算，全都依赖你当初选的那个形状。

            
一句话说清目的：趁改动还免费的时候，把形状定下来。

          

          

            

              
How it used to work以前是怎么做的

                
  • One enormous "reporting table" with 180 columns, most of them empty for most rows.
  • New question → add three more columns. Nobody dared remove any.
  • Historical values overwritten, so last year's report changed every time someone updated a record.
  • Every analyst wrote their own definition of "active customer." There were nine.

                
  • 一张巨大的"报表宽表"，180 列，其中大部分对大部分行都是空的。
  • 来一个新问题就再加三列，而且没人敢删任何一列。
  • 历史值被覆盖，所以每次有人更新一条记录，去年的报表就跟着变。
  • 每个分析师都自己定义"活跃客户"。总共有九种定义。

              
→

              
How it works now现在是怎么做的

                
  • Star schema: a narrow fact table of events, surrounded by small descriptive dimension tables.
  • New question → usually a new join, not a new column.
  • History is preserved deliberately (slowly changing dimensions), so old reports still reproduce.
  • Definitions live in one modelled layer that everyone queries. One definition, agreed once.

                
  • 星型模型：一张窄的事实表记录发生的事件，周围环绕若干小的描述性维度表。
  • 来一个新问题，通常是加一次连接，而不是加一列。
  • 历史被刻意保留（缓慢变化维），所以旧报表依然能复现。
  • 定义集中在一个建模层里，所有人都查它。一个定义，一次达成一致。

            

          

          

            

              🧪 Designing the freezer layout before you fill it🧪 在装满之前先设计好冷冻柜的布局
              
Anyone can shove boxes in a freezer. A good layout means that six months later, someone who has never met you can find every sample from a given study in thirty seconds.

              
The workhorse pattern is the star schema: one fact table in the middle recording events that happened (one row per test performed, with the numbers), surrounded by dimension tables describing the things involved (patient, site, instrument, date).

              
谁都会往冷冻柜里塞盒子。好的布局意味着半年后，一个从没见过你的人能在三十秒内找到某个课题的全部样本。

              
最主力的模式是星型模型：中间一张事实表记录发生过的事件（一行 = 做过的一次检测，带数值），周围是描述相关事物的维度表（病人、厂区、仪器、日期）。

            

            
Three questions to ask before you create any table建任何一张表之前先问的三个问题
              

                
1. What does one row mean? Say it in a full sentence — "one row is one test performed on one sample by one instrument." If you can't say it cleanly, the table is wrong. This is called the grain, and getting it wrong is the most expensive mistake in data modelling.

                
2. What makes a row unique? Which column, or combination, can never repeat? If nothing does, you can't safely re-run anything.

                
3. What happens when the source changes? A patient moves city. Do you overwrite, or keep history so last year's report still reproduces?

                
1. 一行代表什么？用一个完整句子说出来——"一行 = 一台仪器对一份样本做的一次检测"。说不利索，这张表就是错的。这叫粒度，搞错它是数据建模里最贵的错误。

                
2. 什么让一行唯一？哪一列、或哪几列的组合永远不会重复？如果没有，你就没法安全地重跑任何东西。

                
3. 源数据变了会怎样？病人搬到另一个城市。你是覆盖旧值，还是保留历史让去年的报表仍能复现？

              

            

          

          

            

              
If you can't state the grain: your fact table will silently mix levels — some rows are per-test, some are per-batch — and every SUM is quietly wrong. This is the single hardest bug class to detect, because the totals look reasonable.

              
If you always overwrite instead of keeping history: you lose the ability to answer "what did we believe at the time?" Regulators, auditors and post-mortems all ask exactly that question.

              
If every team models its own version: you end up in the meeting where marketing says 40,000 active customers and finance says 31,000, and the next two hours are spent on definitions instead of decisions.

              
如果说不清粒度：你的事实表会悄悄混入不同层级——有些行是按检测的、有些是按批次的——于是每一次 SUM 都在无声地出错。这是最难发现的一类 bug，因为总数看起来很合理。

              
如果永远覆盖而不保留历史：你就失去了回答"我们当时相信的是什么"的能力。监管、审计和事故复盘问的恰恰就是这个问题。

              
如果每个团队各建各的模型：你会开上那种会——市场部说四万活跃客户，财务说三万一，接下来两小时全花在讨论定义而不是做决策上。

◈ Real-world example◈ 真实场景

          
A customer relocates from Penang to Ipoh. Marketing runs last year's regional report again and the numbers have changed.

          
The dimension table overwrote the city, so every historical order that customer ever placed now counts as Ipoh. Last year's report no longer reproduces — and if it was ever filed with a regulator or used in a board pack, you now have two different official versions of the same year.
The fix is a design decision made in advance: keep a row per version of the customer with valid-from and valid-to dates, and join on the date of the order. It costs a little complexity forever, and it buys you the ability to say "here is exactly what we knew, and when" — which is the only defensible answer when someone asks.

          
一个客户从槟城搬到怡保。市场部重跑去年的区域报表，发现数字变了。

          
维度表把城市覆盖掉了，于是这个客户历史上所有订单现在都算到怡保头上。去年的报表不再可复现——而如果它曾经报给监管或进过董事会材料，你现在就有了同一年的两个官方版本。
解法是一个提前做出的设计决定：为客户的每个版本各存一行，带生效起止日期，按订单日期做连接。它会永久带来一点复杂度，换来的是你能说出"这就是我们当时知道的，以及在什么时候知道的"——当有人来问时，这是唯一站得住脚的答案。

        

      


      

        

          ⚡ Challenge⚡ 挑战
          
Build something that runs every night without you做一个每晚自己跑、不用你在场的东西

          ★★★
        

        

          
Pick a public data source that changes daily — air quality, exchange rates, transit delays, weather, your country's open-data portal. Build the full pipeline: pull it, clean it, store it, and let history accumulate.

          
Then earn the hard part. Make it survive being run twice. Make it refuse to load garbage — assert the row count is in range and key columns have no nulls, and fail loudly if not. Make it tell you what it did in a log line you could read half asleep. Schedule it. Leave it alone for two weeks.

          
挑一个每天都在变的公开数据源——空气质量、汇率、交通延误、天气、你所在国家的开放数据门户。搭一条完整的管道：拉取、清洗、入库，并让历史数据一天天累积起来。

          
然后去挣那个难的部分。让它跑两遍也不出错。让它拒绝写入垃圾——断言行数在合理范围、关键列没有空值，不满足就大声失败。让它把做了什么告诉你，一行你半睡半醒也读得懂的日志。设成定时任务，然后两周别管它。

          
You've won when达成条件
            Two weeks later you open the database and there are fourteen days of clean history you never touched — and on the day the source was down, the log says so instead of the table containing zeros.
            两周后你打开数据库，里面有十四天你从没碰过的干净历史——而在数据源挂掉的那一天，日志会明说，而不是表里静静躺着一堆 0。

          
Show me how to approach it给我一点思路
            

              
1. Land the raw response first, untouched, with a timestamp — before any cleaning. When you get the transformation wrong (you will), you can rebuild from raw instead of re-downloading history you can no longer get.

              
2. Decide the grain out loud: "one row is one reading, from one station, at one hour." Write it in a comment at the top of the file.

              
3. Idempotency: delete the rows for the date you're loading, then insert. Now running it five times is identical to running it once. Test that by actually running it five times.

              
4. Validation before load, not after: assert 20 < len(df) < 5000, assert df["station_id"].notna().all(). Then break it on purpose — point it at a bad URL and confirm it screams instead of writing nothing quietly.

              
5. Log one line per run: rows in, rows written, seconds taken. Two weeks later that log is how you'll know it never silently skipped a day.

              
1. 先把原始响应原封不动落地，带时间戳——在任何清洗之前。等你把转换逻辑写错的时候（一定会），你能从原始数据重建，而不是去重新下载一段已经拿不回来的历史。

              
2. 把粒度说出声："一行 = 一个站点、一个小时的一次读数。"把它写在文件开头的注释里。

              
3. 幂等：先删掉本次要加载那一天的行，再插入。这样跑五次和跑一次结果完全一样。而且要真的跑五次来验证。

              
4. 校验放在加载之前，不是之后：assert 20 < len(df) < 5000、assert df["station_id"].notna().all()。然后故意弄坏它——把地址指向一个错的 URL，确认它会尖叫，而不是安静地什么都不写。

              
5. 每次运行记一行日志：读入多少行、写入多少行、耗时多少秒。两周后，正是这份日志能让你确认它从没悄悄漏掉过一天。

            

          

          
Three or four weekends. This is the first thing on your CV that is unambiguously data engineering — not analysis, not scripting. A system that runs without you.三到四个周末。这是你简历上第一件明确属于"数据工程"的东西——不是分析，也不是写脚本，而是一套没有你也能运转的系统。

Computer Science & Cloud Infrastructure计算机原理与云基础设施

      

      
This is the layer most people skip — and it's the layer that separates someone who can write a script from someone who can explain why it takes four hours and how to make it take four minutes. You don't need a CS degree. You need the mental model.

      
这是大多数人跳过的一层——也正是这一层，区分了"会写脚本的人"和"能解释它为什么跑四小时、以及怎么让它跑四分钟的人"。你不需要计算机学位，你需要的是那个心智模型。

      
In plain English — the whole milestone in 4 lines大白话版 —— 四行讲完这个阶段
  • CPU is fast, memory is slower, disk is far slower, network is furthest. Almost every slow thing is walking too far, too often.
  • C is translated once before running. Python is translated line by line, every time — which is why it is slower.
  • pandas is fast because underneath it is not Python. "Vectorise it" means: let that faster layer do the work.
  • The cloud is renting someone else's computers by the minute. Put your database somewhere the internet cannot reach.
  • CPU 最快，内存慢一点，磁盘慢得多，网络最远。几乎所有"慢"，都是走得太远、走得太频繁。
  • C 在运行前一次性翻译完；Python 每次都逐行翻译 —— 这就是它慢的原因。
  • pandas 快，是因为它底下根本不是 Python。"向量化"的意思就是：让底下那层更快的东西去干活。
  • 云就是按分钟租别人的电脑。把你的数据库放在互联网够不到的地方。



      
      

        
1How a computer actually works计算机到底是怎么运转的


        

          

            
            
            
            
          

          

            
Why should a data person care about hardware?做数据的人为什么要关心硬件？

            
Because every performance problem you will ever face is the same story in different clothes: something is walking to the cold room too many times.

            
Without this model, "it's slow" is a mystery and you'll try random fixes — a bigger machine, more threads, a different library. With it, you can reason: is this reading from disk in a loop? Is it shipping data over the network row by row? Is it running out of RAM and swapping? Three questions, and one of them is almost always the answer.

            
因为你将来遇到的每一个性能问题，都是同一个故事换件衣服：有人在反复跑去冷藏室。

            
没有这个模型，"它很慢"就是个谜，你只能乱试——换更大的机器、加线程、换个库。有了它，你可以推理：它是不是在循环里反复读磁盘？是不是在逐行走网络？是不是内存不够在换页？三个问题，答案几乎总在其中。

          

          

            

              
How it used to work以前是怎样

                
  • CPUs got faster every year, so slow code got faster for free. You could wait for hardware to fix you.
  • Spinning hard disks — a physical arm moving to a physical track. Random reads were catastrophically slow.
  • RAM was scarce and expensive; every byte was budgeted.
  • Scaling up meant one bigger, hotter, more expensive machine.

                
  • CPU 每年都变快，慢代码会自动变快。等硬件替你解决就行。
  • 机械硬盘——一条物理磁臂移动到物理磁道。随机读慢得离谱。
  • 内存又少又贵，每个字节都要精打细算。
  • 扩容 = 换一台更大、更热、更贵的机器。

              
→

              
How it works now现在是怎样

                
  • Single-core speed stopped improving much around 2005. Free speedups ended; now you get more cores, and only parallel code benefits.
  • SSDs removed the moving parts, but disk is still ~1,000× slower than RAM.
  • RAM is plentiful — so "load it all into memory" is often the correct, boring fix.
  • Scaling means more machines, which is why distributed tools (Spark, warehouses) exist at all.

                
  • 单核速度大约在 2005 年后基本停滞。免费提速结束了，现在给你的是更多核，只有并行代码才受益。
  • SSD 去掉了机械部件，但磁盘仍然比内存慢约 1000 倍。
  • 内存变得充裕——所以"全部加载进内存"常常就是那个正确又无聊的解法。
  • 扩容意味着更多台机器，这也正是分布式工具（Spark、数仓）存在的全部理由。

            

            
Why this matters right now: the fact that single-core speed plateaued is the reason your job exists in its current form. If computers had kept doubling in speed, nobody would need distributed data engineering.

            
为什么这件事现在很重要：单核速度触顶，正是你这份工作以今天这种形态存在的根本原因。如果电脑一直在翻倍变快，就没人需要分布式数据工程了。

          

          

            

              🧪 The bench, the shelf, and the cold room🧪 实验台、架子、冷藏室
              
The CPU is you — the only thing that actually does work, and you can only hold one or two tubes at a time. RAM is your benchtop: fast to reach, small, and wiped clean every night (that's why unsaved work vanishes when power is lost). Disk / SSD is the cold room down the corridor: enormous, permanent, and slow — you have to get up and walk there.

              
CPU 是你本人——唯一真正在干活的东西，而且一次只拿得住一两支管。内存是你的操作台：伸手就够到，但小，而且每晚清空（这就是断电后未保存的东西会消失的原因）。磁盘/SSD 是走廊尽头的冷藏室：巨大、永久、但慢——你得站起来走过去。

            

            

              
Why your script died你的脚本为什么挂了

                
MemoryError / process killed = you tried to put more on the benchtop than fits. Fix: process in chunks, or use a tool that streams (Polars, DuckDB).

                
MemoryError / 进程被杀 = 你想往操作台上放的东西超过了它的容量。解法：分块处理，或用支持流式的工具（Polars、DuckDB）。

              
Why your script is slow你的脚本为什么慢

                
Usually not the CPU. It's reading the same file repeatedly, querying row-by-row inside a loop, or shipping data over the network a thousand times. Do the work in bulk, once.

                
通常不是 CPU 的问题。是反复读同一个文件、在循环里逐行查数据库、或者把数据在网络上来回搬一千次。改成批量、一次搞定。

            

          

          

            

              
If you don't have this model: you'll respond to slowness by asking for a bigger machine. Often the machine was never the problem, the money is spent, and the job is still slow — now with a bigger bill attached.

              
The classic beginner pattern: a loop that opens a database connection, runs one query, closes it — a million times. That's a million round trips. The same work as one query returning a million rows, done a million times more expensively.

              
The cloud version of the mistake: reading a file from object storage inside a loop. Each read crosses a network. Ten thousand small reads can take an hour where one bulk read takes four seconds.

              
没有这个模型：一慢你就去申请更大的机器。而机器往往从来不是问题，钱花了，任务还是慢——只是账单更大了。

            You have a table of five timings on the same machine, and you can explain each drop by pointing at a specific layer of the memory hierarchy. Not "it got faster" — why it got faster.

Show me how to approach it给我一点思路
            

              
1. Use time.perf_counter() around each version, and print the ratio against the first. Ratios are what people remember.

              
2. Fix one thing at a time. If you fix three things and it gets 90× faster, you have learned nothing about which one mattered.

              
3. Expect the biggest single win to come from removing round trips — the file open or the per-row query — not from the arithmetic. That is the memory hierarchy telling you where it actually hurts.

              
4. Then push it further than is reasonable: make the file bigger than your RAM. Watch it die. Fix it with chunking, then with DuckDB streaming, and note that DuckDB barely noticed.

              
5. Write the whole thing up in the README with the timing table. This is the single most persuasive artefact a junior engineer can own — it is evidence that you understand what is underneath the code, not just the code.
