Essential Developer Tools必备开发工具

Milestone 1 taught you to write things from scratch. This milestone teaches you to stop. Professional work is mostly assembling well-tested parts other people built, and keeping an impeccable record of what you changed and why.

阶段一教你从零写东西，阶段二教你别再从零写。专业工作的大部分，是把别人写好、验证过的零件组装起来，同时把"你改了什么、为什么改"记录得无可挑剔。

In plain English — the whole milestone in 4 lines大白话版 —— 四行讲完这个阶段
  • A framework is pre-built plumbing. You write the small part that is actually yours.
  • Git is a notebook for code: every change dated, signed, and undoable.
  • GitHub is where the team's notebooks live, plus a colleague reading yours before it counts.
  • Open source means you can read the recipe — which is the only way to really trust a tool.
  • 框架是别人搭好的水电管路，你只写真正属于你的那一小块。
  • Git 是给代码用的记录本：每次改动都有日期、有署名、可撤销。
  • GitHub 是全组记录本存放的地方，外加一位同事在它生效前先读一遍。
  • 开源意味着配方你能读到 —— 这是真正信任一个工具的唯一方式。

1Frameworks — React and Flask框架 —— React 与 Flask

Why use someone else's code instead of writing your own?为什么要用别人的代码而不是自己写？

Because the boring parts are also the dangerous parts. Parsing an HTTP request, escaping user input so it can't inject SQL, setting the right security headers, handling half-uploaded files — none of it is interesting, all of it has been got wrong catastrophically by smart people, and all of it is already solved.

The purpose in one line: a framework lets you spend your attention on the 5% of the system that is actually yours, and inherit twenty years of other people's bug fixes for the other 95%.

因为无聊的部分同时也是危险的部分。解析 HTTP 请求、转义用户输入以防 SQL 注入、设置正确的安全响应头、处理只上传了一半的文件——没有一件是有趣的，每一件都被聪明人搞砸过而且后果严重，而每一件都已经被解决了。

一句话说清目的：框架让你把注意力花在真正属于你的那 5%，剩下 95% 直接继承别人二十年的踩坑修复。

How it used to work以前是怎么做的
  • Every team wrote its own routing, own session handling, own database layer. Every company had a slightly different, slightly broken version.
  • Security was whatever the most senior person happened to remember.
  • A new hire needed three months to learn one company's homemade stack — knowledge that was worthless anywhere else.
  • 每个团队自己写路由、自己写会话管理、自己写数据库层。每家公司都有一套略有不同、略有毛病的版本。
  • 安全取决于组里最资深那个人当时恰好记得什么。
  • 新人要三个月才能学会一家公司自制的那套东西——而这份知识换一家公司就一文不值。
→
How it works now现在是怎么做的
  • A handful of frameworks are used by millions. Bugs are found by strangers and fixed before they reach you.
  • Security defaults are on unless you deliberately turn them off.
  • A new hire who knows Flask is productive on day two — anywhere in the world.
  • Upgrading brings you improvements you didn't ask for and didn't have to write.
  • 少数几个框架被几百万人使用。bug 由陌生人发现，在传到你这之前就被修好了。
  • 安全默认是开着的，除非你主动关掉。
  • 一个会 Flask 的新人第二天就能干活——在世界任何地方。
  • 升级一次，就白拿一堆你没要求、也不用自己写的改进。

The trade you're making: you give up total control and accept the framework's opinions. That is almost always a good trade — but it's why you should still understand what's underneath, so that when the framework's opinion is wrong for your case, you can tell.

你在做的这笔交易：放弃完全控制权，接受框架的"主张"。这几乎总是笔划算的交易——但也正因如此，你仍然要懂底下那层，这样当框架的主张不适合你的场景时，你分得出来。

🧪 Nobody synthesises their own buffer🧪 没人自己配缓冲液

You could make PBS from raw salts every morning. You don't — you buy it pre-made, validated, consistent. A framework is pre-made infrastructure. You supply only the part that's specific to your problem.

你当然可以每天早上从原料盐配 PBS。但你不会——你买现成的，已验证、批次一致。框架就是现成的基础设施，你只提供你这个问题特有的那一小块。

Honest scope for you: learn Flask (or FastAPI) properly — you will build internal APIs. Learn just enough React to read it — enough to understand what a frontend colleague is asking your API for. Don't sink a month into React.

给你的诚实建议：把 Flask（或 FastAPI）学扎实——你一定会写内部 API。React 学到能读懂就行——够你理解前端同事想从你的 API 拿什么。别在 React 上砸一个月。

If you write your own instead: you will get it 90% right, and the missing 10% will be the security. The classic outcome is an endpoint that concatenates user input straight into SQL — the single most exploited bug in the history of the web, and every framework prevents it by default.

The organisational damage: homemade infrastructure only you understand means you can never hand the project over. It looks like job security. It is actually a cage.

如果坚持自己写：你会做对 90%，而缺的那 10% 恰好是安全。最经典的结局是某个接口把用户输入直接拼进 SQL——网络史上被利用最多的漏洞，而任何框架默认都会挡住它。

组织层面的代价：只有你懂的自制基础设施，意味着这个项目永远交接不出去。看着像职位护城河，实际上是笼子。

The framework is the bottom five layers. Your job is the small green block — and knowing what's under it when it breaks.下面五层是框架给的。你的工作是最上面那个小绿块——以及在它出问题时，知道底下是什么。

◈ Real-world example◈ 真实场景

The quality team wants a page showing live pass rates by site. They ask how long it will take.

Without a framework: two weeks, and you'd be personally responsible for authentication, session handling and input validation. With Flask: a working API by lunchtime, a rough page by the afternoon, in front of real users the next morning — and the parts you didn't write are the parts an auditor would have flagged. The framework didn't just save time. It changed the answer from "next sprint" to "tomorrow," which is the difference between a tool people use and a tool people stopped waiting for.

质量部门想要一个按厂区显示实时合格率的页面。他们问你要多久。

不用框架：两周，而且认证、会话、输入校验都要你一个人负责。用 Flask：午饭前 API 能跑，下午出个粗糙页面，第二天早上就摆在真实用户面前了——而你没写的那些部分，恰恰是审计会挑刺的部分。框架省的不只是时间，它把答案从"下个迭代"变成了"明天"，这就是"大家在用的工具"和"大家已经不等的工具"之间的差别。

2Version control — Git and GitHub版本控制 —— Git 与 GitHub

Why does code need a notebook?为什么代码需要一本记录本？

Three questions come up constantly, and without version control none of them have answers:

"When did this break?" — you need to compare today's code with a version that worked.
"Why is this line here?" — you need the reasoning of the person who wrote it, eight months ago, who may have left.
"Can we undo it?" — you need to go back without losing everything that came after.

The purpose in one line: Git makes every change reversible, attributable and explainable — which is exactly what a lab notebook does for an experiment, and for exactly the same reason.

有三个问题会反复出现，而没有版本控制，它们一个都答不上来：

"这是什么时候坏的？"——你需要把今天的代码和一个能跑的版本对比。
"这行为什么在这？"——你需要八个月前写它那个人的理由，而那人可能已经离职了。
"能撤回吗？"——你需要退回去，同时不丢掉之后做的所有东西。

一句话说清目的：Git 让每一次改动都可撤销、可追责、可解释——这正是实验记录本对实验做的事，理由也完全一样。

How it used to work以前是怎么做的
  • report_v2_final_FINAL_usethis.py. Seven copies of a folder, and nobody sure which one is live.
  • Two people editing the same file meant one person's work silently vanished.
  • History lived in email threads, or in one person's memory.
  • "Who changed this and why?" was usually unanswerable.
  • report_v2_final_FINAL_usethis.py。同一个文件夹七个副本，没人确定哪个在跑。
  • 两个人改同一个文件，其中一个人的工作就无声消失了。
  • 历史记录存在邮件线程里，或者某个人的记忆里。
  • "这是谁改的、为什么改？"通常答不上来。
→
How it works now现在是怎么做的
  • One folder. Every version ever, retrievable, with dates and authors.
  • Parallel branches let ten people work at once without touching each other's files.
  • Every change carries a written reason, permanently attached.
  • Pull requests mean a second person reads it before it reaches production — peer review for code.
  • 一个文件夹。历史上每一个版本都能取回，带日期和作者。
  • 并行的分支让十个人同时干活，互不碰对方的文件。
  • 每次改动都带一段书面理由，永久附在上面。
  • Pull Request 意味着上线前有第二个人读过——代码版的同行评议。

Where it's heading: Git is now the trigger for everything else. Push a branch and tests run automatically; merge it and it deploys itself. The commit isn't just a record any more — it's the button that starts the machine.

它正在往哪走：Git 现在是一切的触发器。推一个分支，测试自动跑；合并进去，它自己就上线了。提交不再只是记录——它是启动整台机器的那个按钮。

🧪 This is your lab notebook🧪 这就是你的实验记录本

A proper lab notebook is dated, signed, never erased. Git is that, for code. And it has one thing your paper notebook never did: you can start a branch — a parallel copy where you try a risky new protocol without touching the version that currently works. Fails? Throw the branch away. Works? Merge it back.

一本合格的实验记录本：有日期、有签名、从不涂改。Git 就是代码版的它。而且它有一件纸质记录本永远做不到的事：你可以开一条分支——一份平行副本，在上面试危险的新方案，完全不碰当前能用的版本。失败？丢掉分支。成功？合并回去。

git clone <url>              # copy a repo, once / 克隆仓库，一次
git status                   # what have I changed? RUN CONSTANTLY / 常敲
git checkout -b my-feature   # start a new branch / 开新分支
git add .                    # stage changes / 暂存改动
git commit -m "message"      # write the notebook entry / 写记录
git push                     # send to GitHub / 推上去
git pull                     # get everyone else's work / 拉别人的
git log --oneline            # read the history / 看历史

# That's 95% of daily Git. / 日常 Git 的 95% 就这些。
# BAD — tells a future reader nothing / 差：未来的人看不懂
git commit -m "fix"
git commit -m "updates"

# GOOD — says WHAT and WHY / 好：说清做了什么、为什么
git commit -m "Reject samples below 0.95 purity in QC step

The lab changed its acceptance threshold in March.
Previously we passed anything above 0.90, which let
14 bad batches through in Q1."

# Test: will this make sense to you in eight months,
# at 11pm, when something is broken? Write for that person.
# 检验标准：八个月后的深夜、系统坏了的时候，你还看得懂吗？
# 就是写给那个人看的。
# Undo the last commit, keep the file changes
# 撤销上一次提交，但保留文件改动
git reset --soft HEAD~1

# Throw away uncommitted mess / 丢掉未提交的改动
git checkout -- .

# What did I actually change? / 我到底改了什么
git diff

# Merge conflict — Git marks it like this:
# 合并冲突 —— Git 会在文件里这样标出来：
<<<<<<< HEAD
threshold = 0.90        # their version / 对方的
=======
threshold = 0.95        # your version / 你的
>>>>>>> my-feature

# Delete the markers, keep the right line, commit.
# It happens every week. It is not a disaster.
# 删掉标记，留下对的那行，提交。每周都会遇到，不是灾难。

If you use folder copies instead: within a month you'll have pipeline_v3_new_FIXED and no idea which is running in production. The day you need to roll back, you will roll back to the wrong one.

If you commit but never branch: every experiment happens on the live version. One bad afternoon and the thing that was working this morning is gone, with nothing to return to.

If your commit messages say "fix": in six months the history is useless. Git can tell you what changed, but only your message can tell anyone why — and "why" is the only thing that actually helps at 3am.

如果你用复制文件夹的方式：一个月内你就会有 pipeline_v3_new_FIXED，而且不知道生产上跑的是哪个。真需要回滚那天，你会回滚到错的那个。

如果只提交、从不开分支：每次试验都直接在线上版本进行。一个糟糕的下午之后，今早还好好的东西就没了，而且没有可退回的地方。

如果提交信息写"fix"：半年后这份历史就是废纸。Git 能告诉你改了什么，但只有你的留言能告诉别人为什么——而凌晨三点真正有用的只有"为什么"。

▶ Playground▶ 动手玩

Click the commands in any order. The graph draws what actually happens to your history — including the mistakes. Try committing on a branch and then merging. Then try committing directly on main while a branch is open, and merge — that's how conflicts are born.按任意顺序点这些命令。图会画出你的历史真实发生了什么——包括你犯的错。试试在分支上提交再合并；然后试试分支还开着时直接在 main 上提交再合并——冲突就是这么产生的。

◈ Real-world example◈ 真实场景

A dashboard has been showing slightly wrong revenue for an unknown number of weeks. Nobody knows when it started.

With Git, this is a twenty-minute job. git log on the pipeline file shows every change with a date. You find a commit from six weeks ago titled "simplify currency handling," read the diff, and see that someone removed a rounding step. You know the exact date, the exact author to ask, and the exact line to revert — and you can prove to finance which weeks are affected.
Without Git, this is an archaeology project with no artefacts. You'd be guessing, and you'd never be able to tell finance which numbers to trust.

某个看板的收入数字一直略有偏差，已经持续了不知道几周，没人知道从什么时候开始的。

有 Git，这是二十分钟的活。对那个管道文件敲 git log，每次改动带日期一目了然。你找到六周前一个叫"简化币种处理"的提交，读 diff，发现有人删掉了一步四舍五入。你立刻知道确切日期、该问谁、该回滚哪一行——而且能向财务证明受影响的是哪几周。
没有 Git，这就是一场没有文物的考古。你只能猜，而且永远没法告诉财务哪些数字可以信。

3Open source — libraries and models开源 —— 库与模型

Why would anyone give away code — and why should you care?为什么有人白送代码 —— 你为什么该在意？

Because software has almost zero copying cost, and a tool used by a million people gets debugged by a million people. Giving it away is often the fastest route to a tool that actually works.

For you, the reason to care is verifiability. Open source is a published protocol with the full recipe attached — you can read it, test it, and know exactly what it does to your data. Closed software is a black-box kit: often excellent, but you take its word for it, and if the vendor discontinues it you are stranded.

因为软件的复制成本几乎为零，而一个被一百万人使用的工具会被一百万人调试。白送出去，往往是让工具真正可用的最快路径。

对你来说，值得在意的理由是可验证性。开源就是一份连完整配方一起发表的方案——你能读它、测它，确切知道它对你的数据做了什么。闭源软件是一个黑盒试剂盒：常常很好用，但你只能信它的说法，而且供应商一停产你就被困住了。

How it used to work以前是怎么做的
  • You bought a licence, got a compiled binary, and could never see inside.
  • A bug meant filing a ticket and waiting for the next quarterly release.
  • Vendor lock-in was the business model, and price rises were unarguable.
  • AI models, similarly, were entirely behind an API — rent only.
  • 你买一份授权，拿到一个编译好的程序，永远看不到里面。
  • 发现 bug 就提工单，然后等下一个季度版本。
  • 供应商锁定就是商业模式，涨价你也没得谈。
  • AI 模型同理，完全藏在 API 后面——只能租。
→
How it works now现在是怎么做的
  • Most of the stack — Python, Postgres, Linux, pandas, Kubernetes — is open and free to read.
  • You can fix a bug yourself today rather than wait a quarter.
  • The same split has arrived for AI: open-weight models (Llama, Mistral, Qwen, DeepSeek) run on your own hardware, so sensitive data never leaves the building.
  • Companies fund the projects they depend on, because the alternative is maintaining a fork alone.
  • 技术栈的绝大部分——Python、Postgres、Linux、pandas、Kubernetes——都是开放可读的。
  • 发现 bug 今天就能自己修，不用等一个季度。
  • AI 也出现了同样的分化：开放权重模型（Llama、Mistral、Qwen、DeepSeek）可以跑在自己的硬件上，敏感数据不出楼。
  • 公司会资助自己依赖的项目，因为另一条路是独自维护一个分叉。

How to judge whether an open-source library is safe to depend on怎么判断一个开源库能不能依赖

Before you add anything to a project, spend two minutes checking:

1. Recent commits. Has anyone touched it in the last six months?
2. Open issues. Hundreds of unanswered bug reports is a warning.
3. Licence. MIT and Apache-2.0 are permissive and safe for commercial work. GPL has obligations — ask before using.
4. Downloads. Wide use means bugs have been found by someone other than you.
5. Who maintains it. A single unpaid person is a real risk; a foundation or a company is steadier.

在往项目里加任何东西之前，花两分钟检查：

1. 最近的提交。过去半年有人动过吗？
2. 未关闭的 issue。几百个没人回的 bug 报告是警告信号。
3. 许可证。MIT 和 Apache-2.0 宽松，商用安全。GPL 有义务条款——用之前先问。
4. 下载量。用的人多，意味着 bug 是别人先踩到的。
5. 谁在维护。只有一个没报酬的个人是真实风险；基金会或公司维护更稳。

If you add libraries without checking: you inherit an abandoned dependency with a known security hole, and you find out from a compliance scan rather than from yourself.

If you ignore licences: a GPL library in a commercial product can legally oblige your company to publish its source. That is a conversation with legal that nobody enjoys, and it is entirely avoidable by reading one line.

If you only ever use hosted AI: you may be sending customer data to a third party without realising it. Knowing that open-weight models exist is what gives you a second option when someone says "this data cannot leave."

如果不检查就加库：你会继承一个已被弃坑、带已知安全漏洞的依赖，而且是合规扫描先发现，不是你先发现。

如果无视许可证：商业产品里混进 GPL 库，法律上可能要求你们公司公开源码。这是一场没人喜欢的法务对话，而只要读一行字就能完全避免。

如果只会用托管 AI：你可能在不知情的情况下把客户数据发给了第三方。知道有开放权重模型这条路，才是别人说"这批数据不能出去"时你还有第二个选择的原因。

◈ Real-world example◈ 真实场景

Legal says the customer contract data cannot be sent to any external service. Management still wants AI summarisation of it.

If your only mental model is "AI = call an API," this is a dead end and the project dies. If you know open-weight models exist, the answer is: run a mid-sized open model on a machine inside the company network. It's somewhat less capable than the frontier model, needs a GPU, and someone has to maintain it — but the data never leaves, legal signs off, and the project ships. Knowing the option existed is the entire contribution.

法务说客户合同数据不能发给任何外部服务，但管理层仍然想用 AI 做摘要。

如果你脑子里只有"AI = 调 API"，这就是死路，项目就没了。如果你知道有开放权重模型，答案就是：在公司内网的一台机器上跑一个中等规模的开源模型。它比前沿模型弱一些、需要 GPU、还得有人维护——但数据不出门，法务签字，项目落地。知道"还有这个选项"，本身就是全部的贡献。

Rescue a script that only one person knows how to run拯救一个"只有一个人会跑"的脚本

★★☆

Every team has one: a script that lives in someone's Downloads folder, has hard-coded paths, and is emailed around as an attachment. Find yours — or write a deliberately bad one — and turn it into something a stranger could run.

Repository. README that assumes zero knowledge. Config instead of hard-coded paths. A branch, a pull request, a merge. Then wrap the useful part in a Flask endpoint so a colleague can get the answer without running anything at all.

每个团队都有这么一个：躺在某人下载文件夹里、路径写死、靠邮件附件传来传去的脚本。找出你们的那一个——或者故意写一个很糟的——然后把它变成一个陌生人也能跑起来的东西。

建仓库。写一份假设读者零基础的 README。用配置替代写死的路径。开分支、提 PR、合并。最后把有用的那部分包成一个 Flask 接口，让同事什么都不用跑就能拿到答案。

You've won when达成条件 Someone who has never seen it can clone the repo, follow the README, and get the right answer — without messaging you. 一个从没见过它的人，能克隆仓库、照着 README 操作、拿到正确答案——全程不用来问你。
Show me how to approach it给我一点思路

1. Commit it as-is first, warts and all. That ugly first commit is your before-photo, and Git will keep it forever.

2. Write the README before you clean the code. Writing "how to run this" is what exposes every hidden assumption — you will find three things that only work on your laptop.

3. Move every path, threshold and credential into a config file or environment variable. Nothing secret goes in the repo. Ever.

4. Now the discipline: make the change on a branch, open a pull request against your own main, and review your own diff as if a stranger wrote it. You will find something.

5. Wrap the core function in Flask: @app.route("/report"). The script becomes a service, and the answer becomes a link you can send.

1. 先原封不动提交一次，丑就丑。那次难看的初始提交是你的"改造前照片"，Git 会永远替你留着。

2. 在清理代码之前先写 README。写"怎么运行"这件事，会把所有隐藏假设都暴露出来——你会发现有三个地方只在你的笔记本上成立。

3. 把所有路径、阈值、凭据移进配置文件或环境变量。任何机密都不进仓库。永远不。

4. 然后是纪律：在分支上改动、对自己的 main 提 PR、像审别人写的代码一样审自己的 diff。你一定会发现点什么。

5. 用 Flask 把核心函数包起来：@app.route("/report")。脚本变成了服务，答案变成了一条你能发出去的链接。

Two weekends. This single exercise is the difference between "she wrote a script" and "she owns a tool the team uses."两个周末。仅这一件事，就区分了"她写了个脚本"和"她维护着一件全组在用的工具"。

Check yourself · Milestone 2自我检验 · 阶段二

You're about to try a risky change to a pipeline that currently runs in production. What do you do first?你打算对一个正在生产环境运行的管道做一次有风险的改动。第一步做什么？

A branch. Folder copies are how you end up with six versions and no idea which one is live. The branch keeps the working version untouched and gives your colleague something reviewable before it touches production.开分支。复制文件夹的结局就是六个版本、不知道哪个在跑。分支让能用的版本原封不动，同时在碰到生产之前给同事一个可以评审的东西。
