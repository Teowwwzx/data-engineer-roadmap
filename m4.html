Data Engineering Core数据工程核心

Everything so far was foundation. This is the work itself: taking data that arrives messy, incomplete and inconsistent, and turning it into something a scientist or an executive can trust without asking you first.

前面全是打地基。这一段是工作本身：把脏的、不全的、前后不一致的数据，变成科学家或高管不用先问你就敢信的东西。

In plain English — the whole milestone in 4 lines大白话版 —— 四行讲完这个阶段
  • Data always arrives dirty. Six quick checks catch the errors that never throw an error.
  • A pipeline is a scheduled script that collects, cleans and stores — the same way every night.
  • It must survive being run twice, and it must fail loudly rather than load garbage quietly.
  • Modelling is deciding what one row means, before you have ten million of them.
  • 数据到手时永远是脏的。六项快速检查，专抓那些不会报错的错误。
  • 管道就是一个定时脚本：采集、清洗、入库 —— 每晚都用同一种方式。
  • 它必须跑两遍也没事，而且要大声失败，而不是悄悄写进垃圾数据。
  • 建模就是在你还没有一千万行之前，先想清楚"一行代表什么"。
🧪 You are running the sample prep, not the assay🧪 你做的是样本前处理，不是检测本身

In the lab, the analysis is only as good as the prep. If the sample is contaminated, mislabelled, or degraded, the most elegant instrument in the building gives you a beautiful wrong number. Data engineering is sample prep at industrial scale — and the analysts downstream trust your output the way you trust a clean sample. That trust is your entire product.

在实验室里，分析的上限取决于前处理。样本被污染、贴错标签、降解了，楼里最精密的仪器也只会给你一个漂亮的错数。数据工程就是工业规模的样本前处理——下游的分析师信任你的输出，就像你信任一份干净的样本。这份信任，就是你的全部产品。

1Data manipulation — Python (and a little R)数据处理 —— Python（外加一点 R）

Why not just use Excel?为什么不直接用 Excel？

Excel is genuinely excellent for looking at data. It is terrible at repeating a process, because there's no record of what you did. Six months later nobody can tell which cells were typed by hand, which were formulas, and which were pasted from somewhere else.

A script is a protocol: it states every step, it runs identically every time, and someone else can read it and disagree with you. The purpose in one line: turn a set of manual decisions into a reviewable, repeatable procedure.

Excel 看数据确实非常好用，但它极不擅长重复一个过程，因为没有任何记录说明你做了什么。半年后没人分得清哪些格子是手打的、哪些是公式、哪些是从别处粘来的。

脚本就是一份方案：它写明每一步，每次运行结果一致，而且别人能读它、能跟你争论。一句话说清目的：把一堆手工决定，变成一个可评审、可重复的流程。

How it used to work以前是怎么做的
  • Download a CSV, open it, sort, filter, delete some rows, save as _clean_v3.xlsx.
  • Charts made by hand, pasted into slides that go stale the moment they're sent.
  • Everything capped by what fits in memory on one laptop.
  • The knowledge of "how we calculate this" lived in one person's head.
  • 下载一个 CSV，打开、排序、筛选、删几行，另存为 _clean_v3.xlsx。
  • 图表手工做好粘进幻灯片，发出去那一刻就已经过期。
  • 一切受限于一台笔记本内存装得下多少。
  • "这个指标我们是怎么算的"，只存在某个人脑子里。
→
How it works now现在是怎么做的
  • A script reads the raw file, applies named transformations, and writes a clean table — same result every run.
  • Charts regenerate from live data; nothing is ever "as of last Tuesday" by accident.
  • Bigger than memory? Polars or DuckDB stream it, or the warehouse does the work in place.
  • The calculation is in Git, reviewed, and survives the person who wrote it.
  • 脚本读原始文件、施加一系列命名好的转换、写出一张干净的表——每次跑结果都一样。
  • 图表从实时数据重新生成，不会莫名其妙"截止到上周二"。
  • 数据比内存大？用 Polars 或 DuckDB 流式处理，或者让数仓原地算。
  • 算法存在 Git 里、被评审过，而且比写它的人活得久。

The newest shift: pandas is no longer the only answer. Polars and DuckDB handle datasets far larger than memory on a normal laptop, and DuckDB lets you run SQL directly on Parquet files with no database server at all. Learn pandas first — then know these exist for the day pandas says MemoryError.

最新的变化：pandas 不再是唯一答案。Polars 和 DuckDB 能在普通笔记本上处理远大于内存的数据集，而 DuckDB 让你不用任何数据库服务就能直接对 Parquet 文件跑 SQL。先学 pandas——然后记住这两个的存在，留给 pandas 报 MemoryError 的那天。

The default. Better for pipelines, automation, integration with everything else. Learn read_csv, filtering, groupby, merge, fillna, and dates.

默认选择。更适合做管道、自动化、和其他一切集成。重点学 read_csv、筛选、groupby、merge、fillna，以及日期处理。

df = pd.read_csv("samples.csv", parse_dates=["collected_at"])

# 1. look before you leap / 先看再动
print(df.shape, df.dtypes, df.isna().sum(), sep="\n\n")

# 2. clean / 清洗
df = df.dropna(subset=["sample_id"])            # no ID = unusable
df["lab_site"] = df["lab_site"].str.strip().str.upper()
df = df.drop_duplicates(subset=["sample_id"], keep="last")

# 3. derive / 派生
df["passed"] = (df["purity"] >= 0.95) & (df["volume_ml"] >= 1.0)

# 4. aggregate / 汇总
summary = (df.groupby(["lab_site", df["collected_at"].dt.to_period("M")])
             .agg(n=("sample_id", "count"), pass_rate=("passed", "mean"))
             .reset_index())

If you skip the six checks: you will publish a number that is wrong in a way nobody can see. A date column read as text sorts "10 Jan" before "2 Feb". A duplicated key silently doubles a total. Neither throws an error — that's what makes them dangerous.

If you clean data by hand each time: the cleaning is un-reviewable and un-repeatable. When the source changes format next quarter, you won't remember what you did last time, and neither will anyone else.

If you don't document null-handling decisions: "we dropped rows with missing volume" is a scientific choice that changes the result. Undocumented, it becomes an invisible bias baked into every downstream report.

如果跳过那六项检查：你会发布一个错得没人看得出来的数字。日期列被当成文本，排序时"10 Jan"排在"2 Feb"前面；主键重复会悄悄把总数翻倍。这两者都不会报错——这才是它们危险的地方。

如果每次都手工清洗：清洗过程不可评审、不可重复。下季度源数据改格式时，你不记得上次怎么做的，别人也不知道。

如果不记录空值处理的决定："我们丢掉了体积缺失的行"是一个会改变结果的科学选择。不写下来，它就变成一个被烘进所有下游报表里的隐形偏差。

◈ Real-world example◈ 真实场景

A regional manager escalates: "Ipoh's numbers look 30% lower than they should. Are we losing samples?"

No samples were lost. value_counts() on lab_site shows IPOH (400), Ipoh (23) and "ipoh " (7) — one site being reported as three, because two upstream systems capitalise differently and one has a trailing space from a form field. Every group-by silently split the site three ways.
Cost of the fix: one line. Cost of not having checked: three weeks of a manager mistrusting the dashboard, and a meeting about whether the plant has a process problem.

区域经理升级投诉："怡保的数字比应该的低了 30%，我们是不是在丢样本？"

没有丢样本。对 lab_site 跑一次 value_counts()：IPOH（400）、Ipoh（23）、"ipoh "（7）——同一个厂区被算成了三个，因为上游两个系统大小写规则不同，还有一个表单字段带了尾随空格。每次分组统计都悄悄把这个厂区拆成三份。
修复成本：一行代码。没检查的成本：经理三周不信任看板，外加一场"工厂是不是流程有问题"的会议。

2ETL pipelinesETL 数据管道

Why not query the source systems directly?为什么不直接查源系统？

Four reasons, and each one on its own would justify a pipeline.

1. You'd take production down. An analyst's exploratory query on the live order system can lock tables the business needs to take orders.
2. The shapes don't match. Source systems are built to write one record fast. Analysis needs to read a million records fast. Those are opposite designs.
3. History disappears. Source systems overwrite. When a customer changes address, last year's report silently changes too — unless someone captured the old value.
4. Nothing joins. The CRM says "Acme Corp", finance says "ACME Corporation", the shipping system says customer #4471. Someone has to decide those are the same company, once, in one place.

四个原因，任何一个单独拿出来都足以支撑建一条管道。

1. 你会把生产环境搞挂。分析师在线上订单系统做的探索性查询，可能锁住业务下单要用的表。
2. 结构对不上。源系统的设计目标是快速写一条记录，分析需要的是快速读一百万条。这是两种相反的设计。
3. 历史会消失。源系统是覆盖写的。客户改了地址，去年的报表也会悄悄跟着变——除非有人把旧值保存下来。
4. 拼不起来。CRM 里叫"Acme Corp"，财务系统叫"ACME Corporation"，物流系统叫客户 #4471。得有人在某一处、一次性地判定这是同一家公司。

Classic ETL (1990s–2010s)经典 ETL（1990s–2010s）
  • Extract → Transform → Load. Transform before loading, because warehouse storage was expensive.
  • Raw data was thrown away after transformation. Got the logic wrong? The original is gone.
  • Built by dragging boxes in a proprietary GUI tool. Not reviewable, not in version control.
  • Ran overnight; you found out about failures the next morning, from a user.
  • 抽取 → 转换 → 加载。先转换再入库，因为数仓存储很贵。
  • 转换完原始数据就丢了。逻辑写错了？原件已经没了。
  • 用商业 GUI 工具拖框搭出来，不可评审，不进版本控制。
  • 半夜跑，出问题第二天早上从用户那里才知道。
→
Modern ELT现代 ELT
  • Extract → Load → Transform. Land the raw data first; transform inside the warehouse. Storage got cheap.
  • Raw is kept forever, so you can rebuild everything when a definition changes — and you will.
  • Transformations are SQL files in Git, reviewed in pull requests, tested (dbt).
  • Orchestrators (Airflow, Dagster, Prefect) retry, alert, and show you exactly which step failed.
  • 抽取 → 加载 → 转换。先把原始数据落地，再在数仓里转换。因为存储变便宜了。
  • 原始数据永久保留，定义一变就能全量重建——而定义一定会变。
  • 转换逻辑是 Git 里的 SQL 文件，走 PR 评审，有测试（dbt）。
  • 调度器（Airflow、Dagster、Prefect）会重试、告警，并明确告诉你哪一步失败了。

Why the flip happened: cloud storage costs collapsed while warehouse compute became elastic. Once keeping raw data is nearly free, throwing it away is just risk with no upside. If you learn one modern habit, learn this one: never destroy the raw input.

为什么会反转：云存储成本塌了，而数仓算力变成弹性的。一旦保留原始数据几乎免费，丢掉它就只剩风险、没有好处。如果只学一个现代习惯，学这个：永远不要销毁原始输入。

🧪 Extract, Transform, Load = collect, prep, store🧪 抽取、转换、加载 = 采集、前处理、入库

Extract — collect the raw sample from wherever it lives. Transform — the prep bench: clean, standardise units, remove contaminants, derive what you need. Load — store the finished, labelled preparation where everyone can find it.

The critical property is the same one your protocols have: reproducibility. Run it twice on the same input, get the same output. If a pipeline can't be re-run safely, it isn't a pipeline — it's a one-off you'll be nervous about forever.

抽取——从数据所在的任何地方把原始样本采集过来。转换——前处理台：清洗、统一单位、去除杂质、派生你需要的指标。加载——把处理好、贴好标签的成品存到大家都能找到的地方。

最关键的性质和你的实验方案一样：可复现。同样的输入跑两次，得到同样的输出。一条不能安全重跑的管道就不是管道——它只是一次性的东西，你会一直为它提心吊胆。

The four properties every production pipeline needs生产级管道必须具备的四个性质

1. Idempotent. Re-running doesn't duplicate or corrupt anything. Rerun-safety is what lets you sleep.

2. Observable. It logs what it did, how many rows, how long. When someone asks "did last night's run work?", you should not have to guess.

3. Validated. It checks its own output — row counts in range, no nulls in key columns, no impossible values — and fails loudly rather than quietly loading garbage.

4. Recoverable. When it fails at 3am (it will), it's obvious where it stopped and safe to restart from there.

1. 幂等。重跑不会重复或损坏任何东西。重跑安全，你才睡得着。

2. 可观测。它记录自己做了什么、多少行、跑了多久。有人问"昨晚跑成功了吗"，你不该靠猜。

3. 有校验。它检查自己的输出——行数在合理范围、关键列无空值、没有不可能的数值——发现问题就大声失败，而不是悄悄写进垃圾数据。

4. 可恢复。凌晨三点它挂掉时（一定会），能一眼看出停在哪，并且能安全地从那里重启。

Batch vs streaming批处理 vs 流处理

Batch runs on a schedule and covers most needs. Streaming processes each event as it arrives. Start with batch. Only go streaming when someone can articulate why minutes-old data isn't good enough.

批处理按计划运行，覆盖绝大多数需求。流处理逐条实时处理。先做批处理。只有当有人能说清"为什么几分钟前的数据不够用"时，再上流处理。

Tools you'll hear about你会听到的工具

Airflow / Dagster / Prefect for scheduling; dbt for SQL transformations; Great Expectations or Soda for validation. Learn the concepts — the tools are interchangeable and will be replaced.

Airflow / Dagster / Prefect 做调度；dbt 做 SQL 转换；Great Expectations 或 Soda 做校验。要学的是概念——工具可以互换，也终将被替换。

If your pipeline isn't idempotent: the first failed-and-rerun night doubles your numbers. Revenue looks like it grew 100%, someone celebrates, and then someone else has to un-celebrate.

If it isn't validated: it will happily load a day of zeros because an upstream API returned an error page instead of data. Silence is the worst possible failure mode — an error at least tells you.

If it isn't observable: "is the data fresh?" becomes unanswerable, and people stop trusting the whole warehouse. Trust is lost far faster than it's rebuilt.

If you transform before loading and throw away raw: the day someone changes the definition of "active customer," you cannot recompute history. You'll have to say "our numbers only go back to today," which is a genuinely painful sentence.

如果管道不幂等：第一个"失败后重跑"的夜晚就会让数字翻倍。收入看起来涨了 100%，有人开始庆祝，然后另一个人得去取消庆祝。

如果没有校验：上游 API 返回了一个错误页面而不是数据，它会高高兴兴地写进一整天的 0。无声失败是最糟的失败方式——至少报错还会告诉你。

如果不可观测："数据是不是最新的？"变成没法回答的问题，然后人们开始不信任整个数仓。信任崩塌的速度远快于重建的速度。

如果先转换再加载、还丢掉原始数据：等哪天有人改了"活跃客户"的定义，你没法重算历史。你只能说"我们的数据只能从今天开始"——这是一句真的很难说出口的话。

◈ Real-world example◈ 真实场景

The nightly job fails at 02:40 on a network blip. You re-run it at 09:00. By 09:05 the revenue dashboard shows double.

The pipeline appended rows instead of replacing them, so yesterday is now in the table twice. Nothing errored — the numbers are simply wrong, and three people have already seen them.
The fix, in order of preference: delete-then-insert for the affected date range, or an upsert keyed on (date, site, sample_id). Both make a re-run a no-op instead of a duplication. The lesson: design for the re-run before the failure — the failure is guaranteed, and it will happen at the least convenient hour.

凌晨 2:40 网络抖动导致每晚任务失败。你 9:00 重跑了一次。9:05 收入看板显示的数字翻了一倍。

管道是追加而不是替换，所以昨天的数据现在在表里有两份。没有任何报错——数字就是错的，而且已经有三个人看到了。
修复方式，按优先级：对受影响的日期区间先删后插，或者按 (date, site, sample_id) 做 upsert。两者都能让重跑变成"什么都没发生"而不是"翻倍"。教训：在失败之前就为重跑做设计——失败是必然的，而且一定发生在最不方便的时刻。

3Data modelling数据建模

Why design the tables before you fill them?为什么要在装满之前先设计好表？

Because a table's shape decides which questions are cheap and which are impossible. Get it right and "pass rate by region by quarter for instruments overdue for calibration" is one join. Get it wrong and the same question needs a week and a apologetic email.

And unlike code, data models are extremely hard to change later — because by then a hundred queries, five dashboards and someone's bonus calculation all depend on the shape you chose.

The purpose in one line: decide the shape while it's still free to decide.

因为表的形状决定了哪些问题是廉价的、哪些是不可能的。设计对了，"按区域、按季度、只看超期未校准的仪器的合格率"就是一次连接。设计错了，同样的问题要花一周，外加一封道歉邮件。

而且和代码不同，数据模型后期极难修改——因为到那时，一百条查询、五个看板、还有某人的奖金计算，全都依赖你当初选的那个形状。

一句话说清目的：趁改动还免费的时候，把形状定下来。

How it used to work以前是怎么做的
  • One enormous "reporting table" with 180 columns, most of them empty for most rows.
  • New question → add three more columns. Nobody dared remove any.
  • Historical values overwritten, so last year's report changed every time someone updated a record.
  • Every analyst wrote their own definition of "active customer." There were nine.
  • 一张巨大的"报表宽表"，180 列，其中大部分对大部分行都是空的。
  • 来一个新问题就再加三列，而且没人敢删任何一列。
  • 历史值被覆盖，所以每次有人更新一条记录，去年的报表就跟着变。
  • 每个分析师都自己定义"活跃客户"。总共有九种定义。
→
How it works now现在是怎么做的
  • Star schema: a narrow fact table of events, surrounded by small descriptive dimension tables.
  • New question → usually a new join, not a new column.
  • History is preserved deliberately (slowly changing dimensions), so old reports still reproduce.
  • Definitions live in one modelled layer that everyone queries. One definition, agreed once.
  • 星型模型：一张窄的事实表记录发生的事件，周围环绕若干小的描述性维度表。
  • 来一个新问题，通常是加一次连接，而不是加一列。
  • 历史被刻意保留（缓慢变化维），所以旧报表依然能复现。
  • 定义集中在一个建模层里，所有人都查它。一个定义，一次达成一致。
🧪 Designing the freezer layout before you fill it🧪 在装满之前先设计好冷冻柜的布局

Anyone can shove boxes in a freezer. A good layout means that six months later, someone who has never met you can find every sample from a given study in thirty seconds.

The workhorse pattern is the star schema: one fact table in the middle recording events that happened (one row per test performed, with the numbers), surrounded by dimension tables describing the things involved (patient, site, instrument, date).

谁都会往冷冻柜里塞盒子。好的布局意味着半年后，一个从没见过你的人能在三十秒内找到某个课题的全部样本。

最主力的模式是星型模型：中间一张事实表记录发生过的事件（一行 = 做过的一次检测，带数值），周围是描述相关事物的维度表（病人、厂区、仪器、日期）。

Three questions to ask before you create any table建任何一张表之前先问的三个问题

1. What does one row mean? Say it in a full sentence — "one row is one test performed on one sample by one instrument." If you can't say it cleanly, the table is wrong. This is called the grain, and getting it wrong is the most expensive mistake in data modelling.

2. What makes a row unique? Which column, or combination, can never repeat? If nothing does, you can't safely re-run anything.

3. What happens when the source changes? A patient moves city. Do you overwrite, or keep history so last year's report still reproduces?

1. 一行代表什么？用一个完整句子说出来——"一行 = 一台仪器对一份样本做的一次检测"。说不利索，这张表就是错的。这叫粒度，搞错它是数据建模里最贵的错误。

2. 什么让一行唯一？哪一列、或哪几列的组合永远不会重复？如果没有，你就没法安全地重跑任何东西。

3. 源数据变了会怎样？病人搬到另一个城市。你是覆盖旧值，还是保留历史让去年的报表仍能复现？

If you can't state the grain: your fact table will silently mix levels — some rows are per-test, some are per-batch — and every SUM is quietly wrong. This is the single hardest bug class to detect, because the totals look reasonable.

If you always overwrite instead of keeping history: you lose the ability to answer "what did we believe at the time?" Regulators, auditors and post-mortems all ask exactly that question.

If every team models its own version: you end up in the meeting where marketing says 40,000 active customers and finance says 31,000, and the next two hours are spent on definitions instead of decisions.

如果说不清粒度：你的事实表会悄悄混入不同层级——有些行是按检测的、有些是按批次的——于是每一次 SUM 都在无声地出错。这是最难发现的一类 bug，因为总数看起来很合理。

如果永远覆盖而不保留历史：你就失去了回答"我们当时相信的是什么"的能力。监管、审计和事故复盘问的恰恰就是这个问题。

如果每个团队各建各的模型：你会开上那种会——市场部说四万活跃客户，财务说三万一，接下来两小时全花在讨论定义而不是做决策上。

Animation · a star schema动画 · 星型模型

"Pass rate by region, by quarter, for instruments overdue for calibration" — one join away, instead of a week of work."按区域、按季度、只看超期未校准仪器的合格率"——一次连接就够了，而不是一周的工作量。

◈ Real-world example◈ 真实场景

A customer relocates from Penang to Ipoh. Marketing runs last year's regional report again and the numbers have changed.

The dimension table overwrote the city, so every historical order that customer ever placed now counts as Ipoh. Last year's report no longer reproduces — and if it was ever filed with a regulator or used in a board pack, you now have two different official versions of the same year.
The fix is a design decision made in advance: keep a row per version of the customer with valid-from and valid-to dates, and join on the date of the order. It costs a little complexity forever, and it buys you the ability to say "here is exactly what we knew, and when" — which is the only defensible answer when someone asks.

一个客户从槟城搬到怡保。市场部重跑去年的区域报表，发现数字变了。

维度表把城市覆盖掉了，于是这个客户历史上所有订单现在都算到怡保头上。去年的报表不再可复现——而如果它曾经报给监管或进过董事会材料，你现在就有了同一年的两个官方版本。
解法是一个提前做出的设计决定：为客户的每个版本各存一行，带生效起止日期，按订单日期做连接。它会永久带来一点复杂度，换来的是你能说出"这就是我们当时知道的，以及在什么时候知道的"——当有人来问时，这是唯一站得住脚的答案。

⚡ Challenge⚡ 挑战

Build something that runs every night without you做一个每晚自己跑、不用你在场的东西

★★★

Pick a public data source that changes daily — air quality, exchange rates, transit delays, weather, your country's open-data portal. Build the full pipeline: pull it, clean it, store it, and let history accumulate.

Then earn the hard part. Make it survive being run twice. Make it refuse to load garbage — assert the row count is in range and key columns have no nulls, and fail loudly if not. Make it tell you what it did in a log line you could read half asleep. Schedule it. Leave it alone for two weeks.

挑一个每天都在变的公开数据源——空气质量、汇率、交通延误、天气、你所在国家的开放数据门户。搭一条完整的管道：拉取、清洗、入库，并让历史数据一天天累积起来。

然后去挣那个难的部分。让它跑两遍也不出错。让它拒绝写入垃圾——断言行数在合理范围、关键列没有空值，不满足就大声失败。让它把做了什么告诉你，一行你半睡半醒也读得懂的日志。设成定时任务，然后两周别管它。

You've won when达成条件 Two weeks later you open the database and there are fourteen days of clean history you never touched — and on the day the source was down, the log says so instead of the table containing zeros. 两周后你打开数据库，里面有十四天你从没碰过的干净历史——而在数据源挂掉的那一天，日志会明说，而不是表里静静躺着一堆 0。
Show me how to approach it给我一点思路

1. Land the raw response first, untouched, with a timestamp — before any cleaning. When you get the transformation wrong (you will), you can rebuild from raw instead of re-downloading history you can no longer get.

2. Decide the grain out loud: "one row is one reading, from one station, at one hour." Write it in a comment at the top of the file.

3. Idempotency: delete the rows for the date you're loading, then insert. Now running it five times is identical to running it once. Test that by actually running it five times.

4. Validation before load, not after: assert 20 < len(df) < 5000, assert df["station_id"].notna().all(). Then break it on purpose — point it at a bad URL and confirm it screams instead of writing nothing quietly.

5. Log one line per run: rows in, rows written, seconds taken. Two weeks later that log is how you'll know it never silently skipped a day.

1. 先把原始响应原封不动落地，带时间戳——在任何清洗之前。等你把转换逻辑写错的时候（一定会），你能从原始数据重建，而不是去重新下载一段已经拿不回来的历史。

2. 把粒度说出声："一行 = 一个站点、一个小时的一次读数。"把它写在文件开头的注释里。

3. 幂等：先删掉本次要加载那一天的行，再插入。这样跑五次和跑一次结果完全一样。而且要真的跑五次来验证。

4. 校验放在加载之前，不是之后：assert 20 < len(df) < 5000、assert df["station_id"].notna().all()。然后故意弄坏它——把地址指向一个错的 URL，确认它会尖叫，而不是安静地什么都不写。

5. 每次运行记一行日志：读入多少行、写入多少行、耗时多少秒。两周后，正是这份日志能让你确认它从没悄悄漏掉过一天。

Three or four weekends. This is the first thing on your CV that is unambiguously data engineering — not analysis, not scripting. A system that runs without you.三到四个周末。这是你简历上第一件明确属于"数据工程"的东西——不是分析，也不是写脚本，而是一套没有你也能运转的系统。

Check yourself · Milestone 4自我检验 · 阶段四

Your nightly pipeline failed halfway through and you re-ran it. Revenue in the dashboard is now double. What was missing?你的每晚管道跑到一半失败，你重跑了一次。现在看板上的收入翻倍了。缺的是什么？

Idempotency. The pipeline appended the same rows a second time. Usual fixes: delete-then-insert for the affected range, or an upsert on a unique key. Design for the re-run before the failure, because the failure is guaranteed.幂等性。管道把同样的行又追加了一遍。常见修法：对受影响区间先删后插，或按唯一键 upsert。在失败之前就为重跑做设计，因为失败是必然的。

value_counts() on your lab_site column returns: IPOH (400), Ipoh (23), "ipoh " (7). What is this?对 lab_site 列跑 value_counts() 得到：IPOH（400）、Ipoh（23）、"ipoh "（7）。这是什么情况？

One site, three spellings — exactly why check #6 exists. Left alone, every group-by silently splits Ipoh into three, and nobody notices until a regional manager asks why their numbers look low.一个厂区，三种写法——这正是第 6 项检查存在的理由。放着不管，每次分组都会悄悄把怡保拆成三份，直到区域经理来问"为什么我的数字这么低"才有人发现。
