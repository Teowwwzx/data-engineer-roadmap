IT BasicsIT 基础

Goal for these three months: stop feeling lost when people talk. You are not trying to become a web developer. You are learning the four words every single conversation in this building is built from — frontend, backend, database, API.

这三个月的目标只有一个：别人开会讲话时，你不再一脸茫然。你不是要变成前端工程师，你是在学这栋楼里每一场对话都建立其上的四个词——前端、后端、数据库、API。

In plain English — the whole milestone in 4 lines大白话版 —— 四行讲完这个阶段
  • Frontend is the part you can see. It runs on your own computer, inside the browser.
  • Backend is the part you cannot see. It runs on someone else's computer and holds the rules.
  • Database is where the facts are kept, in tables, so nothing gets lost or duplicated.
  • API is the standard form these three use to talk to each other. HTTP is the post office that carries it.
  • 前端是你看得见的那部分，跑在你自己的电脑上、浏览器里。
  • 后端是你看不见的那部分，跑在别人的电脑上，规则都在它手里。
  • 数据库是事实存放的地方，存成表，这样东西不会丢也不会重。
  • API 是这三者互相说话时用的标准表单，而 HTTP 是负责送这张表的邮局。
🧪 The lab analogy🧪 实验室类比

Think of a diagnostic lab that patients walk into. The frontend is the reception desk — the only part the patient sees, where they fill in a form. The backend is the lab bench behind the door — where the actual analysis happens, following a protocol. The database is the sample freezer and the record archive — everything stored, labelled, and retrievable. And the API is the request slip that travels between them: a standard form saying "run test X on sample Y," so reception and the bench never have to guess what the other means.

想象一间病人会走进来的检验科。前端是前台——病人唯一看得见的部分，在那里填表。后端是门后面的实验台——按标准流程真正做分析的地方。数据库是样本冷冻柜和档案室——所有东西都存好、贴好标签、随时能取出来。而 API 就是在它们之间来回传递的申请单：一张格式固定的表，写着"对 Y 号样本做 X 项检测"，这样前台和实验台永远不用猜对方是什么意思。

1Frontend fundamentals — HTML, CSS, JavaScript前端基础 —— HTML、CSS、JavaScript

Why does the frontend exist at all?为什么会有"前端"这个东西？

Because a computer's data is unreadable to a human. A database row is ("S-001",0.98,1,"2026-03-14"). A person needs a heading, a colour, a button, an ordering. The frontend exists purely to translate machine truth into human understanding — and to translate human intent (a click, a typed number) back into something the machine can act on.

Its purpose in one line: it is the negotiating layer between a system that only understands structure and a person who only understands meaning.

因为电脑里的数据人是读不懂的。数据库里一行记录长这样：("S-001",0.98,1,"2026-03-14")。而人需要标题、颜色、按钮、排序。前端存在的唯一目的，就是把机器的事实翻译成人能理解的东西——再把人的意图（一次点击、输入的一个数字）翻译回机器能执行的指令。

一句话说清它的目的：它是"只懂结构的系统"和"只懂意义的人"之间的谈判层。

How it used to work以前是怎么做的
  • Every click sent a request to the server, which sent back a whole new page. The screen went white and reloaded.
  • HTML, styling and behaviour were tangled in one file — <font color="red"> sat right in the content.
  • A different page had to be hand-written for every combination of data.
  • 每点一次，浏览器就向服务器要一整个新页面，屏幕闪白、整页刷新。
  • 结构、样式、行为全混在一个文件里——<font color="red"> 直接写在内容中间。
  • 数据有多少种组合，就得手写多少个页面。
→
How it works now现在是怎么做的
  • The page loads once. JavaScript fetches only the data that changed and redraws just that part.
  • Strict separation: HTML = structure, CSS = appearance, JS = behaviour. Change the colour scheme without touching the content.
  • One template + data renders a thousand different views.
  • 页面只加载一次，JavaScript 只去取变化的数据，然后局部重绘那一小块。
  • 严格分工：HTML 管结构，CSS 管外观，JS 管行为。改配色不用碰内容。
  • 一套模板加上数据，就能渲染出上千种不同的视图。

Why the change happened: networks stayed slow while screens got more interactive. Sending 2 KB of JSON instead of a 200 KB page is a hundred-fold saving, repeated on every single click.

为什么会这样演进：网络速度没跟上，但界面越来越需要交互。每次点击传 2 KB 的 JSON 而不是 200 KB 的整页，就是一百倍的节省，而且每点一次都省一次。

Three languages, three jobs, and they never overlap. HTML is the structure. CSS is the appearance. JavaScript is the behaviour.

三种语言，三份工作，互不越界。HTML 管结构，CSS 管外观，JavaScript 管行为。

🧪 Think of a conference poster🧪 想象一张学术海报

HTML is the content you wrote — title, sections, the figure, the references. CSS is the layout and design — font sizes, colour scheme, where the figure sits. JavaScript is what happens when someone walks up and interacts — a slider that changes the plot, a button that reveals raw data. Take CSS away and your poster is still readable, just ugly. Take HTML away and there is nothing to style.

HTML 是你写的内容——标题、章节、图、参考文献。CSS 是排版和设计——字号、配色、图放在哪。JavaScript 是有人走过来跟它互动时发生的事——拖动滑块图就变、点按钮显示原始数据。去掉 CSS，海报还能读，只是难看；去掉 HTML，就没有东西可以被美化了。

How deep should you go? As a data engineer: shallow, but real. Read a page's HTML, know what a <div> is, write ten lines of JavaScript. You do not need to master CSS layout. Two weekends is enough.

该学到多深？作为数据工程师：浅，但要真懂。能读懂一个页面的 HTML、知道 <div> 是什么、能写十行 JavaScript 就够了。你不需要精通 CSS 布局。两个周末足够。

If you never learn any frontend: you can still do the job — but you become dependent. When a dashboard shows a wrong number, you won't be able to tell whether your pipeline sent bad data or the page displayed good data badly. That's a whole class of bug you cannot debug alone, and you'll be waiting on someone else's calendar to find out.

The other failure mode: designing an API without knowing how it will be consumed. You'll return data in a shape that forces the frontend to do ten transformations, and they'll quietly stop asking you for things.

如果你完全不碰前端：工作照样能做——但你会变得依赖别人。当看板上某个数字不对时，你没法判断是你的管道送错了数据，还是页面把对的数据显示错了。这一整类 bug 你独立排查不了，只能等别人有空。

另一个坑：设计 API 时不知道对方要怎么用。你返回的数据结构会逼前端做十次转换，然后他们就慢慢不来找你了。

2Backend — Python, your primary instrument后端 —— Python，你最主要的仪器

Why is there a "backend" separate from the page?为什么要有一个和页面分开的"后端"？

Three reasons, and they're all about trust.

1. You cannot trust the browser. Anything running on a user's machine can be edited by that user. If the price check happens in JavaScript, a determined person changes the price to zero. Rules that matter must run somewhere the user cannot reach.

2. You cannot ship the data. The browser can't hold ten million rows, and you wouldn't want it to — it would mean handing every user the entire database.

3. One truth, many screens. The web app, the mobile app and the nightly report must all apply the same QC rule. Write it once in the backend, and all three get the same answer forever.

三个原因，而且全都关于信任。

1. 浏览器不可信。任何跑在用户机器上的东西，用户都能改。如果价格校验写在 JavaScript 里，有心人把价格改成 0 就行。真正重要的规则必须跑在用户碰不到的地方。

2. 数据不能整个发过去。浏览器装不下一千万行，你也不希望它装得下——那等于把整个数据库交给每一个用户。

3. 一份真相，多个屏幕。网页、手机 App、每晚的报表，必须用同一条 QC 规则。在后端写一次，这三个地方永远得到同一个答案。

How it used to work以前是怎么做的
  • One giant program did everything — UI, logic and data access welded together. Change one line, retest the world.
  • It ran on one specific server in one specific room. If that machine died, so did the product.
  • Deploying meant a person copying files over FTP at 2am and hoping.
  • Scaling meant buying a bigger machine (and waiting six weeks for it to arrive).
  • 一个巨大的程序包办一切——界面、逻辑、数据访问焊死在一起。改一行，就得把整个系统重测一遍。
  • 它跑在某个机房里的某一台特定服务器上。那台机器一挂，产品就没了。
  • 发布 = 有个人凌晨两点用 FTP 把文件拷上去，然后祈祷。
  • 扩容 = 买一台更大的机器（然后等六周才到货）。
→
How it works now现在是怎么做的
  • Small independent services, each with one job, talking over APIs. Change one without touching the rest.
  • It runs in a container — a sealed box that behaves identically on your laptop and in the cloud.
  • Deploying is automatic: push to Git, tests run, it ships itself.
  • Scaling is a number in a config file. Ten copies for the busy hour, one for the night.
  • 拆成一个个小服务，每个只干一件事，之间用 API 对话。改一个不用动其他的。
  • 它跑在容器里——一个密封的盒子，在你笔记本上和在云上表现完全一致。
  • 发布是自动的：推到 Git、自动跑测试、自己上线。
  • 扩容只是配置文件里的一个数字。高峰期开十个副本，夜里留一个。

What this means for you: "it works on my machine" stopped being an acceptable sentence around 2015. The container is the answer to it, and it's why you'll meet Docker in year two.

这对你意味着什么：大概从 2015 年起，"在我机器上是好的"就不再是一句能被接受的话了。容器就是对这句话的回答，也是你第二年一定会遇到 Docker 的原因。

🧪 A program is a written protocol🧪 程序就是一份写下来的实验方案

You already write protocols: a numbered list of steps, precise enough that a different person in a different lab gets the same result. A Python script is exactly that, written for a machine that follows instructions perfectly and literally — it will never notice that step 4 obviously meant millilitres. That literalness is the whole difficulty and the whole power.

你早就在写实验方案了：编号的步骤，精确到换一个人、换一间实验室也能做出同样的结果。Python 脚本就是这个，只不过读者是一台完美而且字面执行指令的机器——它永远不会"看出来"第四步说的显然是毫升。这种绝对字面，既是全部的难处，也是全部的力量。

Learn in this order按这个顺序学

Variables → lists & dictionaries → if/for → functions → reading files → error handling → importing libraries. Stop there. That is 90% of what you use daily.

变量 → 列表和字典 → if/for → 函数 → 读文件 → 错误处理 → 导入第三方库。学到这里就停。这已经覆盖了你日常用到的 90%。

Skip for now现在先跳过

Classes and object-oriented design, decorators, async, metaclasses. You will meet them naturally later, and they make no sense before you have written real scripts.

类和面向对象、装饰器、异步、元类。以后自然会遇到；在你写过真正的脚本之前，学它们完全没有意义。

# A protocol, written for a machine / 写给机器看的实验方案
def qc_check(sample):
    """Pass a sample only if purity is high AND volume is enough."""
    if sample["purity"] >= 0.95 and sample["volume_ml"] >= 1.0:
        return "PASS"
    return "FAIL"

samples = [
    {"id": "S-001", "purity": 0.98, "volume_ml": 2.4},
    {"id": "S-002", "purity": 0.91, "volume_ml": 3.0},
    {"id": "S-003", "purity": 0.99, "volume_ml": 0.4},
]

for s in samples:
    print(s["id"], "→", qc_check(s))
S-001 → PASS
S-002 → FAIL   # purity too low / 纯度不够
S-003 → FAIL   # volume too low / 体积不够

# Note S-003: purity was excellent, but the machine
# does not care. Both conditions must be true because
# you wrote "and". This literalness is the whole game.
#
# 注意 S-003：纯度非常好，但机器不在乎。因为你写的是
# "and"，两个条件必须同时成立。这种字面执行就是全部。

If you try to do data work without real Python: you stay stuck at the size of a spreadsheet. Excel gives up somewhere around a million rows, and long before that it gives up on reproducibility — nobody can tell which cells were typed by hand and which were formulas, and last month's version can't be re-run.

The specific damage: every monthly report becomes four hours of manual clicking that only you know how to do. You become the bottleneck, permanently, and you cannot take a holiday.

如果不真正学会 Python 就做数据工作：你永远被卡在电子表格的量级上。Excel 到一百万行左右就撑不住了，而在那之前很久，它就已经撑不住可复现性了——没人分得清哪些格子是手打的、哪些是公式，上个月那版也没法重跑一次。

具体的代价：每月报表变成四小时的手工点击，而且只有你会点。你会永久性地成为瓶颈，连假都不敢休。

◈ Real-world example◈ 真实场景

The lab changes its purity threshold from 0.90 to 0.95, effective immediately.

If that rule lives in a spreadsheet formula, someone has to find and update it in fourteen files, and two of them will be missed. If it lives in one Python function in the backend, you change one number, commit it with a message explaining why, and every screen and every report in the company is correct within minutes — including the one the regulator will ask about next year, because Git can prove exactly when the rule changed and who changed it.

实验室把纯度阈值从 0.90 改成 0.95，即刻生效。

如果这条规则写在表格公式里，就得有人去十四个文件里找出来改掉，而且一定会漏掉两个。如果它是后端的一个 Python 函数，你只改一个数字，提交时写清楚为什么改，几分钟内全公司每一块屏幕、每一份报表都是对的——包括明年监管来问的那一份，因为 Git 能准确证明规则是什么时候改的、谁改的。

3Databases — SQL and relational tables数据库 —— SQL 与关系表

This is the single most valuable skill in your job. If you learn only one thing exceptionally well this year, make it SQL.

这是你这份工作里最值钱的一项技能。如果这一年只能把一件事学到出类拔萃，就选 SQL。

Why split data into separate tables at all?为什么非要把数据拆成好几张表？

Because the same fact stored twice will eventually disagree with itself. That is not a risk — it is a certainty, and it's the reason the entire relational model exists.

Imagine one giant sheet where every row repeats a patient's full name, address and date of birth for every test they ever had. Change one address and you must find twelve rows. Miss one, and your data now contains two different truths about the same person. Six months later nobody knows which is right.

The purpose in one line: store each fact exactly once, in exactly one place, so there is only ever one version of the truth to correct.

因为同一个事实存两遍，迟早会自己跟自己矛盾。这不是"有风险"，这是必然，也是整个关系模型存在的理由。

想象一张巨大的表，病人每做一次检测，就重复记一遍他的全名、地址、出生日期。地址改一次，你得找出十二行来改。漏掉一行，你的数据里就有了关于同一个人的两个版本。半年后，没人知道哪个是对的。

一句话说清目的：每个事实只存一次、只存一处，这样需要更正时永远只有一个版本。

How it used to work以前是怎么做的
  • Data lived in flat files, one giant file per topic, with everything repeated on every line.
  • To answer a question you wrote a whole program that read the file top to bottom.
  • Two people writing at once corrupted the file. There was no such thing as a safe concurrent update.
  • Changing the format meant rewriting every program that read it.
  • 数据存在平面文件里，一个主题一个大文件，每一行都把所有信息重复一遍。
  • 想回答一个问题，就得写一整个程序把文件从头读到尾。
  • 两个人同时写就会把文件写坏。当时根本没有"安全并发更新"这回事。
  • 格式一改，所有读它的程序都得重写。
→
How it works now现在是怎么做的
  • Data lives in related tables. Each fact once; keys point between them.
  • You describe what you want in SQL. The database figures out how to get it — and it's better at that than you are.
  • Thousands of people write at once safely. Transactions guarantee all-or-nothing.
  • Add a column without breaking a single existing query.
  • 数据存在互相关联的表里。每个事实只存一次，靠"键"互相指向。
  • 你用 SQL 描述要什么，数据库自己决定怎么取——而且它比你更擅长这件事。
  • 成千上万人同时写也安全。事务保证要么全成、要么全不成。
  • 加一列，不会弄坏任何一条已有的查询。

And the newest layer: for analytics, tables are now often stored by column instead of by row (BigQuery, Snowflake, DuckDB, Parquet files). Asking for the average of one column no longer means reading all forty. Same relational idea — different physical layout, ten to a hundred times faster for the questions analysts actually ask.

还有最新的一层：做分析时，表现在常常按列存储而不是按行（BigQuery、Snowflake、DuckDB、Parquet 文件）。求某一列的平均值，不再需要把四十列全读一遍。关系模型没变——只是物理存储方式变了，对分析师真正会问的那类问题，快十倍到一百倍。

🧪 The sample registry, done properly🧪 一份做得对的样本登记册

One table for patients, one table for tests. The test table stores only a small patient_id pointing back. A JOIN is how you temporarily glue them together when you need the full picture — like pulling a sample and its paperwork onto the same bench for as long as you need them, then putting both back where they belong.

一张 patients 表，一张 tests 表。检测表里只存一个小小的 patient_id 指回去。JOIN 就是你需要完整信息时，临时把它们拼在一起——就像把样本和它的档案一起拿到实验台上，用完再各归各位。

SELECT p.name, p.city, t.test_name, t.value
FROM patients AS p
JOIN tests AS t
  ON t.patient_id = p.patient_id;
-- How many tests per city, worst first? / 各城市检测数与均值，最差的排前面
SELECT p.city, COUNT(*) AS n_tests, AVG(t.value) AS avg_value
FROM patients AS p
JOIN tests AS t ON t.patient_id = p.patient_id
WHERE t.test_name = 'Glucose'
GROUP BY p.city
HAVING COUNT(*) > 5
ORDER BY avg_value DESC;
# SQL is written in one order but RUNS in another.
# SQL 写的顺序和实际执行顺序不一样。记住执行顺序，
# 就解决了 90% 的 SQL 困惑。

  1. FROM / JOIN   # get and combine tables / 取表并拼接
  2. WHERE          # throw away rows / 扔掉不要的行
  3. GROUP BY       # bucket what's left / 把剩下的分组
  4. HAVING         # throw away whole buckets / 扔掉整组
  5. SELECT         # pick columns / 选列、算值
  6. ORDER BY       # sort / 排序
  7. LIMIT          # cut / 截断

# This is why WHERE cannot use an alias you created in
# SELECT: SELECT hasn't run yet.
# 这就是为什么 WHERE 用不了你在 SELECT 里起的别名——
# 那时候 SELECT 还没执行。

If you keep everything in one wide table: updates become unsafe. A single spelling correction has to be applied in a hundred places, and the day someone applies it in ninety-nine, your data has quietly forked.

If you avoid SQL and pull everything into Python instead: you move a million rows across the network to compute a number the database could have computed in place in 40 milliseconds. It works at 10,000 rows and collapses at 10 million — and it will collapse in production, not in testing.

The subtle one: without knowing the execution order, you'll write a WHERE that silently turns your LEFT JOIN into an inner join and quietly deletes the exact rows you were investigating.

如果把所有东西塞进一张宽表：更新会变得不安全。改一个拼写要在一百处同步，而当有人只改了九十九处那天，你的数据就悄悄分叉了。

如果绕开 SQL、把数据全拉到 Python 里算：你为了算一个数字，把一百万行搬过网络，而数据库原地 40 毫秒就能算完。一万行时没问题，一千万行时崩掉——而且是在生产环境崩，不是在测试环境。

还有个隐蔽的：不懂执行顺序，你写的 WHERE 会悄悄把 LEFT JOIN 变成内连接，把你正要调查的那些行恰好过滤掉。

◈ Real-world example◈ 真实场景


Finance asks: "Which customers ordered in January but never came back?"


In a spreadsheet this is an afternoon of VLOOKUPs and a result nobody fully trusts. In SQL it's a LEFT JOIN from January orders to all later orders, keeping only the rows where the later side came back empty — about six lines, runs in under a second, and produces the same answer every time anyone runs it. The difference isn't speed of typing. It's that the SQL version is a definition of the question that can be reviewed, corrected, scheduled, and trusted. The spreadsheet is a one-off nobody can audit.


财务问："哪些客户一月份下过单，之后再也没回来过？"


用表格做，这是一下午的 VLOOKUP，而且结果没人完全放心。用 SQL，这就是从"一月订单"到"之后所有订单"的一次 LEFT JOIN，只保留右边为空的那些行——大概六行代码，一秒内跑完，而且不管谁跑、跑多少次，答案都一样。差别不在打字快慢，而在于 SQL 版本是对这个问题的一份定义：可以被审阅、被更正、被定时执行、被信任。表格版本是一次性的，没人能审计。

4Web communication — HTTP and REST APIs网络通信 —— HTTP 与 REST API














Why do systems talk through an API instead of just sharing the database?为什么系统之间要走 API，而不是直接共用数据库？


Because a shared database is a shared fate. If ten applications read your tables directly, you can never rename a column again — you'd break all ten, and you don't even know who they are.


An API is a promise with a boundary: "you may ask me these specific questions, in this specific way, and I promise this specific shape of answer." Behind that boundary you are free to restructure everything. That freedom is the entire product.


The second reason is permission. Direct database access is all-or-nothing. An API can decide, per request, that this caller may see their own samples and not anyone else's.


因为共用数据库等于共担命运。如果十个应用直接读你的表，你就再也别想给某一列改名了——十个全会崩，而且你连它们是谁都不知道。


API 是一个带边界的承诺："你可以用这种方式问我这些特定的问题，我保证给你这种特定形状的答案。"边界背后，你想怎么重构都行。这份自由本身就是它的全部价值。


第二个原因是权限。直连数据库是全有或全无；API 可以针对每一次请求判断：这个调用方只能看自己的样本，看不到别人的。








How it used to work以前是怎么做的


  • Systems integrated by dropping a CSV on a shared drive at midnight and hoping the other side picked it up.
  • Or by connecting straight to each other's database with a shared password.
  • Formats were agreed in a Word document that went out of date immediately.
  • If the file didn't arrive, nobody found out until someone complained the next morning.


  • 系统之间靠半夜往共享盘上丢一个 CSV来集成，然后祈祷对方会去取。
  • 或者干脆用一个共享密码直连对方的数据库。
  • 格式约定写在一份 Word 文档里，而那份文档立刻就过期了。
  • 文件没送到的话，要等第二天早上有人抱怨才会发现。


→


How it works now现在是怎么做的


  • Systems ask each other live, over HTTP, and get an answer in milliseconds.
  • Every caller identifies itself with a token that can be revoked in one click.
  • The format is machine-readable and self-documenting (OpenAPI) — the docs cannot silently drift from reality.
  • Failure is immediate and explicit: a status code, logged, alertable.


  • 系统之间通过 HTTP 实时互问，毫秒级拿到答案。
  • 每个调用方都用令牌表明身份，一键就能吊销。
  • 格式是机器可读、自带文档的（OpenAPI）——文档不可能悄悄和现实脱节。
  • 出错是立刻且明确的：一个状态码，有日志，可以告警。




Where it's heading: the same idea now extends to AI. An agent calling a tool through MCP (Milestone 3) is doing exactly this — a bounded, permissioned, self-describing request. Learn HTTP well and MCP will feel obvious.


它正在往哪走：同一套思路现在延伸到了 AI。Agent 通过 MCP 调用工具（阶段三）做的就是这件事——一次有边界、有权限、自带说明的请求。把 HTTP 学扎实，MCP 会显得理所当然。







🧪 The request slip to the central lab🧪 送去中心实验室的申请单

When your lab sends a sample to a specialised facility, you don't walk in and rummage through their freezer. You fill in their form: which test, which sample, your reference number. They send back a standard report — or a rejection slip explaining what was wrong.


API = that agreed form. HTTP = the courier system. Status code = the rejection slip: 200 done, 404 no such sample, 401 not authorised, 500 we broke something on our end.


你的实验室把样本送去专门机构时，不会自己走进去翻人家的冷冻柜。你填的是他们的表单：做哪项检测、哪份样本、你的编号。他们回一份标准报告——或者一张说明哪里填错了的退单。


API = 那张约定好的表单。HTTP = 快递系统。状态码 = 那张退单：200 完成，404 没有这份样本，401 你没有权限，500 是我们这边坏了。








import requests

resp = requests.get(
    "https://lab.example.com/api/samples/S-001",
    headers={"Authorization": "Bearer abc123"},
    timeout=10,   # always set a timeout / 永远要设超时
)

if resp.status_code == 200:
    data = resp.json()          # JSON text → Python dict
    print(data["purity"])
else:
    print("Request failed:", resp.status_code, resp.text)

201 Created       # worked, something new exists / 成功并新建了资源
400 Bad Request   # YOUR form was wrong / 你的请求格式不对
401 Unauthorized  # you didn't identify yourself / 没表明身份
403 Forbidden     # we know you; still no / 知道你是谁，但不许

# 口诀：4xx 是你的问题，5xx 是对方的问题。










If you integrate by dropping files instead: you inherit an entire category of 3am problems — the file arrived half-written, the file arrived twice, the file didn't arrive and nothing told you. Every one of those needs custom handling you'll write badly the first time.


If you don't learn status codes: you will spend hours debugging your own code when the server was returning 503 the whole time. This is the single most common wasted afternoon in the field.


If you skip timeouts and retries: one slow API hangs your pipeline forever. It doesn't crash — which is worse, because nothing alerts. It just silently stops, and you find out on Thursday.


如果你改用丢文件的方式集成：你会继承一整类凌晨三点的问题——文件传了一半、文件传了两遍、文件根本没到而且没人告诉你。每一种都需要专门处理，而你第一次一定写不好。


如果不记状态码：你会花好几个小时调自己的代码，而对方服务器从头到尾都在返回 503。这是这行里最常见的一个下午。


如果不设超时和重试：一个慢接口能把你的管道永远挂住。它不会崩——这更糟，因为没有任何告警。它只是无声停住，你周四才发现。

◈ Real-world example◈ 真实场景


Your nightly pipeline pulls exchange rates from a vendor API. One morning every figure in the finance report is zero.


You check the logs. The vendor returned 429 Too Many Requests at 02:14 — your retry loop had been hammering them. Your code didn't check the status code, so it parsed the error body, found no rates, and wrote zeros. Nothing crashed. Nothing alerted. The report shipped to the CFO.
The fix is three lines: check the status code, back off exponentially on 429, and fail loudly rather than writing a value you didn't get. Every one of those three habits comes from understanding HTTP rather than just calling it.


你的每晚管道从供应商 API 取汇率。某天早上，财务报表里每个数字都是 0。


你查日志：凌晨 2:14 供应商返回了 429 请求过多——你的重试循环一直在猛敲人家。你的代码没有检查状态码，于是把错误内容当数据解析，没找到汇率，就写了 0。程序没崩，没有告警，报表照常发给了 CFO。
修复只要三行：检查状态码、遇到 429 就指数退避、拿不到数据就大声失败而不是随便写个值。这三个习惯，都来自"理解 HTTP"而不只是"会调 HTTP"。
